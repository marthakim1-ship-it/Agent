# YOVIA 브랜드 레퍼런스 웹사이트 리서치

## 목적

YOVIA 웹사이트 기획의 근거가 되는 글로벌·국내 브랜드 공식 웹사이트 리서치 데이터베이스를 구축한다.

이 Skill은 **원시 리서치 자료를 생성하는 단계**만 담당한다.

- 기존 리서치 자료가 있으면 신규 조사 전에 무결성·구조·상태를 검증한다.
- 기존 자료가 유효하면 전체 신규 웹조사를 생략하고 출력 스키마에 맞게 정규화한다.
- 일부 항목만 불완전하면 누락·오류 항목만 제한적으로 재검증한다.
- 기존 자료가 없거나 사용할 수 없을 때만 공식 웹사이트를 신규 조사한다.
- 브랜드·제품, 웹 구조, 시각 표현, 제품 설명, 인터랙션과 반응형 UX를 동일한 항목으로 기록한다.
- 확인된 사실과 미확인 항목을 구분한다.
- 최대 200개 레코드를 연속된 ID로 관리한다.
- 후속 분류와 분석이 근거를 추적할 수 있도록 페이지 번호를 연결한다.

이 단계에서는 다음 작업을 수행하지 않는다.

- 직접·인접·주변 레퍼런스의 최종 분류
- 200개 사이트의 공통점이나 반복 패턴에 대한 최종 결론
- YOVIA 적용안, 정보 구조, 디자인 제안
- 근거가 없는 수치·기능·브랜드·페이지 생성
- 원본 입력 파일 삭제 또는 이동
- 1팀 창의적 결론 → 2팀 직관적 결론 → 통합 결론 최종 보고

분류·분석·최종 보고는 후속 Skill과 `AGENTS.md`가 담당한다.

## 경로 원칙

1. 프로젝트 루트의 `AGENTS.md`를 먼저 읽고 입력·출력·아카이브 경로와 목표 레코드 수를 확인한다.
2. `AGENTS.md`에 경로가 지정되어 있으면 반드시 그 경로를 따른다.
3. 경로가 지정되어 있지 않으면 기본 출력 경로로 다음을 사용한다.

```text
output/01_research/YOVIA_BRAND_REFERENCE_RESEARCH_200.md
```

4. 기존 결과물의 보존과 실패 결과물의 이동은 `AGENTS.md`의 아카이브 규칙을 따른다.
5. 동일 이름의 기존 결과물을 확인하지 않고 덮어쓰지 않는다.
6. Windows 절대경로를 결과 본문에 반복 기록하지 않고, 프로젝트 루트 기준 상대경로를 사용한다.

## 입력

다음 자료를 우선순위대로 사용한다.

```text
1. 사용자가 현재 요청에서 지정한 파일
2. input/01_research/YOVIA_BRAND_REFERENCE_RESEARCH_200.md
3. ../Antigravity/research/YOVIA_BRAND_REFERENCE_RESEARCH_200.md
4. 기존 output/01_research/YOVIA_BRAND_REFERENCE_RESEARCH_200.md
5. 사용자가 제공한 후보 브랜드 목록 또는 검색 기준
```

프로젝트 루트가 `C:\kje\UIUXA\Md_Skill`이면 Antigravity 상대경로는 다음 파일을 의미한다.

```text
C:\kje\UIUXA\Antigravity\research\YOVIA_BRAND_REFERENCE_RESEARCH_200.md
```

## 기존 자료 우선 처리

기존 리서치 파일을 발견하면 신규 검색 전에 다음 항목을 확인한다.

- 파일 판독 가능 여부
- 실제 레코드 수
- 첫 ID와 마지막 ID
- 중복·누락 ID
- 필수 섹션과 필드 존재 여부
- 동일 공식 도메인 중복 후보
- `completed`, `partial`, `failed` 상태 수
- `active`, `redirected`, `dead` URL 상태 수
- 공식 사이트 확인 근거
- P1~P5 추적 가능 여부
- 비어 있거나 `not_verified`인 필드

### 유효한 기존 자료

다음 조건을 충족하면 신규 전체 웹조사를 수행하지 않는다.

- 파일을 정상적으로 읽을 수 있음
- 레코드 ID와 필수 구조를 식별할 수 있음
- URL 상태와 조사 상태를 계산할 수 있음
- 공식 사이트 근거와 확인 페이지를 추적할 수 있음
- 후속 분류가 사용할 핵심 관찰 필드가 존재함

처리 순서:

```text
기존 자료 읽기
→ 구조·수량·상태 검증
→ 확인된 사실과 근거 유지
→ 현재 출력 스키마에 맞게 정규화
→ output/01_research/YOVIA_BRAND_REFERENCE_RESEARCH_200.md 저장
→ 품질 검사
```

### 일부 불완전한 기존 자료

기존 기록 전체를 버리지 않는다.

- 확인된 사실과 P1~P5 근거는 유지한다.
- 누락·오류·접근 실패 항목만 제한적으로 재검증한다.
- `not_verified`를 억지로 채우지 않는다.
- 200개 전체를 처음부터 다시 조사하지 않는다.
- 변경한 레코드와 변경 근거를 추적 가능하게 유지한다.

### 신규 전체 조사가 허용되는 경우

- 기존 파일이 없음
- 파일 판독 불가
- 필수 구조가 심하게 손상됨
- 공식 사이트 근거와 상태를 추적할 수 없음
- 사용자가 명시적으로 전면 재조사를 요청함

기존 입력 파일은 수정·이동·삭제하지 않는다. 정규화 결과만 출력 경로에 저장한다.

## 조사 범위

후속 분류가 가능하도록 YOVIA와 관련성이 있는 브랜드를 폭넓게 조사한다.

- 요거트, 그릭요거트, 스키르, 마시는 요거트
- 파우치형 식품, 휴대형 아침 식사, 간편식
- 단백질 음료·바, 기능성 식품, 식사 대용식
- DTC 식품과 제품 사용법이 명확한 소비재
- 패키지 컬러, 상품 탐색, 기능 설명, 모바일 구매 UX를 참고할 수 있는 브랜드

이 단계에서는 조사 대상을 미리 직접·인접·주변으로 확정하지 않는다. 최종 분류는 분류 Skill에서 수행한다.

## 조사 단위와 진행 방식

1. 목표 레코드 수는 기본 200개다. 사용자가 다른 수를 지정하면 그 수를 따른다.
2. 레코드는 `001`부터 3자리 연속 ID를 사용한다.
3. 10~20개 단위로 조사하고 각 배치가 끝날 때 결과 파일을 저장한다.
4. 중단 후 재개할 때는 기존 파일의 마지막 유효 ID 다음부터 계속한다.
5. 조사 완료를 선언하기 전에 실제 레코드 수와 ID 연속성을 검사한다.
6. 동일 브랜드나 동일 공식 도메인이 중복 발견되어도 리서치 단계에서 임의 삭제하지 않는다.
7. 중복 후보는 `[객관적 연구 메모]`의 `미확인·추가 확인`에 관계를 명시하고 후속 분류 단계로 넘긴다.

## 공식 사이트 탐색과 검증

### 1. 검색

브랜드별로 공식 사이트를 찾기 위한 검색어를 기록한다.

```text
브랜드명 + official website
브랜드명 + 제품 카테고리 + official
국내 브랜드명 + 공식몰
```

검색 결과의 요약문만으로 관찰 내용을 작성하지 않는다. 검색은 공식 사이트를 발견하기 위한 수단으로만 사용한다.

### 2. 공식 사이트 판정

다음 중 복수 항목이 확인되어야 공식 사이트로 판정한다.

- 브랜드명·로고·상표 표시
- 공식 제품 또는 서비스 라인업
- 회사 소개, 브랜드 스토리, 연락처 또는 정책 페이지
- 공식 판매처·구매·매장 찾기 기능
- 동일 브랜드의 공식 소셜 계정이나 패키지에서 연결되는 도메인
- 기존 공식 도메인에서 최종 도메인으로의 정상 리디렉션

공식성을 확인할 수 없으면 추측하지 않고 `not_verified` 또는 `failed`로 처리한다.

### 3. URL 상태

다음 값만 사용한다.

- `active`: 최종 공식 페이지가 정상적으로 열리고 핵심 콘텐츠를 확인할 수 있음
- `redirected`: 발견 URL이 다른 공식 도메인·국가 사이트·최종 URL로 이동함
- `dead`: 공식 페이지가 사라졌거나 단종·404·접속 실패로 유효한 콘텐츠를 확인할 수 없음

`redirected`인 경우 발견 URL과 최종 URL을 모두 기록한다.

## 확인 페이지

가능한 범위에서 브랜드마다 최대 5개 페이지를 확인한다.

- `P1 메인`: 홈페이지 또는 대표 랜딩 페이지
- `P2 제품 목록 또는 서비스 목록`: 카테고리·라인업·스토어 페이지
- `P3 제품 상세 또는 핵심 기능`: 대표 제품 상세, 패키지 구조, 핵심 기능 페이지
- `P4 추가 확인`: 브랜드 스토리, 레시피, 사용법, 원료, 지속가능성 등
- `P5 추가 확인`: 판매처 찾기, FAQ, 비교, 임팩트, 추가 검증 페이지 등

확인하지 못한 페이지는 URL을 만들지 말고 정확히 `not_verified`로 기록한다.

### P1~P5 역할 검증

- URL 경로명만 보고 페이지 역할을 추정하지 않는다. 실제 공식 페이지의 제목·본문·탐색 요소를 확인하여 P1~P5 역할을 부여한다.
- `P2 제품 목록 또는 서비스 목록`에는 실제 제품군·서비스·메뉴·스토어 목록이 있어야 한다. FAQ, 보관기한, 정책 페이지를 제품 목록으로 기록하지 않는다.
- `P3 제품 상세 또는 핵심 기능`에는 개별 제품 상세, 패키지 구조, 원료·영양, 사용법 또는 핵심 기능 중 하나 이상이 실제로 있어야 한다.
- 하나의 공식 페이지가 복수 역할을 수행할 수 있다. 같은 URL을 여러 P 번호에 쓸 때는 본문에 `P1이 P2 역할을 겸함`처럼 대체 역할과 근거를 명시한다.
- P3가 `not_verified`여도 자동으로 `partial`로 판정하지 않는다. P1·P2·P4·P5 중 공식 페이지가 P3 역할을 대신하면 대체 URL, 대체 역할, 확인한 필드를 `미확인·추가 확인`에 기록한다.
- P3 대체 근거가 없으면 제품 상세·핵심 기능을 추측하지 않고 해당 레코드를 `partial`로 판정한다.
- 검색 결과에서 URL을 발견한 것과 해당 페이지 본문을 확인한 것을 구분한다. 연결만 확인하고 본문을 읽지 못했으면 그 제한을 기록한다.

## 근거 기록 원칙

1. 관찰 내용은 실제로 확인한 페이지에 근거해야 한다.
2. 각 핵심 문장 끝에 근거 페이지를 `(P1)`, `(P2, P3)`처럼 표시한다.
3. 다른 페이지에서 확인한 정보를 한 페이지의 근거인 것처럼 합치지 않는다.
4. 대표 카피는 필요한 짧은 문구만 기록하고, 긴 문장을 복사하지 않는다.
5. 이미지·모션·모바일 동작을 직접 확인하지 못했으면 추론하지 않고 `not_verified`로 쓴다.
6. 검색 결과, 기억, 일반적인 업계 관행을 해당 브랜드의 사실처럼 작성하지 않는다.
7. `partial` 레코드에는 확인된 필드만 작성하고 나머지는 `not_verified`로 남긴다.
8. 사실과 해석을 구분한다.
   - 관찰 섹션: 확인된 사실
   - 객관적 연구 메모: 확인된 사실을 바탕으로 한 제한적 메모
9. 공통점·시장 전체 경향은 이 파일에서 확정하지 않는다. `반복 패턴`은 후속 분석을 위한 후보 메모로만 작성한다.
10. `not_verified`인 P 번호는 확인된 사실의 출처로 사용할 수 없다. 미확인 상태 자체를 P1에서 확인했다는 표현은 가능하지만 미확인 내용을 사실로 확정해서는 안 된다.
11. CTA는 화면에 표시된 실제 문구와 연결 대상을 분리해 기록한다. `View products`를 확인했다는 이유만으로 구매·판매처·구독 연결을 추정하지 않는다.
12. 수치·배지·사용 상황은 실제 관찰 문장과 P 번호가 연결되어야 한다. 회사 연혁·가맹점 수 같은 사업 수치를 제품 정보 수치로 바꾸어 기록하지 않는다.

## 조사 상태

다음 값만 사용한다.

- `completed`: 공식 사이트와 핵심 페이지를 충분히 확인하여 주요 관찰 항목을 근거와 함께 작성함
- `partial`: 공식 사이트는 확인했지만 `completed` 필수 조건을 충족하지 못할 정도로 핵심 페이지·제품 정보·근거가 부족함. 모바일·인터랙션·부가 페이지 일부가 미확인이어도 아래 `completed` 필수 조건을 모두 충족하면 자동으로 `partial`이 되지 않음
- `failed`: 공식 사이트를 검증하지 못했거나 URL이 `dead`여서 유효한 조사가 불가능함

상태 판정 규칙:

- `dead` 레코드는 원칙적으로 `failed`다.
- `partial`은 확인한 정보만 유지하고 빈칸을 추측으로 채우지 않는다.
- P4·P5가 `not_verified`여도 P1~P3의 핵심 정보가 충분하면 `completed`가 가능하다.
- P3가 `not_verified`여도 공식 대체 근거가 P3 역할을 충분히 수행하고 그 URL·역할·한계가 명시되면 `completed`가 가능하다.
- `completed`는 공식 사이트, 핵심 제품·서비스, 제품 목록 또는 이에 준하는 제품군·메뉴, 제품 상세·핵심 기능 또는 공식 대체 근거, 주요 관찰의 P1~P5 추적 가능성을 모두 갖춰야 한다.
- 미확인 모바일·모션·인터랙션을 확인된 사실처럼 사용하거나 위 필수 조건 중 하나라도 충족하지 못하면 `completed`로 두지 않고 `partial` 또는 `failed`로 판정한다.
- 공식 사이트를 찾지 못했는데 2차 자료만 있는 경우 `completed`로 처리하지 않는다.

## 출력 파일 머리말

결과 파일의 시작 부분은 다음 구조를 사용한다.

```md
# YOVIA 브랜드 레퍼런스 웹사이트 200선 종합 분석 데이터베이스
- **프로젝트**: YOVIA (요비아)
- **조사 대상**: 총 {실제 레코드 수}개 글로벌/국내 브랜드 웹사이트
- **최종 업데이트**: YYYY-MM-DD
- **사이트 상태 요약**: Active {수}개 | Redirected {수}개 | Dead {수}개

---
```

목표가 200개여도 실제 레코드가 200개 미만이면 `총 200개`라고 쓰지 않는다. 실제 저장된 레코드 수를 기록한다.

## 품질 검사

저장 전 다음 항목을 모두 검사한다.

### 구조

- 레코드 수가 머리말의 조사 대상 수와 일치하는가?
- ID가 `001`부터 연속되며 중복되지 않는가?
- 각 레코드에 모든 필수 섹션과 필드가 존재하는가?
- 필드 순서가 레코드마다 동일한가?
- 파일 인코딩이 UTF-8인가?
- 파일 끝에 줄바꿈이 있는가?

### 상태

- `active + redirected + dead`의 합이 전체 레코드 수와 같은가?
- 모든 레코드에 URL 상태가 있는가?
- 모든 레코드에 조사 상태가 있는가?
- `dead`가 원칙적으로 `failed`와 연결되는가?
- `partial`의 미확인 필드가 추측으로 채워지지 않았는가?
- 각 `completed` 레코드가 completed 필수 조건을 모두 충족하는가?
- P3가 `not_verified`인 completed 레코드에 공식 대체 URL·역할·한계가 명시되어 있는가?
- 레코드별 `completed + partial + failed`를 다시 세어 머리말 합계와 대조했는가?
- 머리말의 상태 합계가 전체 레코드 수와 정확히 같은가?

### 근거

- 공식 사이트 확인 근거가 구체적인가?
- 핵심 관찰에 P1~P5 근거가 연결되는가?
- 확인하지 않은 페이지·모션·모바일 동작을 지어내지 않았는가?
- 검색 결과나 2차 자료를 공식 사이트 관찰처럼 기록하지 않았는가?
- 대표 카피와 수치를 원문에서 확인했는가?
- 각 P1~P5 URL의 실제 페이지 역할이 표기한 역할과 일치하는가?
- 본문에서 인용한 모든 P 번호가 확인 가능한 공식 근거로 존재하는가?
- `not_verified`인 P 번호를 확인된 사실의 근거로 인용한 사례가 0개인가?
- CTA 문구와 연결 대상이 각각 공식 페이지에서 직접 확인되는가?
- 동일 URL이 여러 P 역할을 겸하면 대체 역할과 이유가 명시되어 있는가?

### 기존 자료 재사용

- 입력 우선순위에 따라 기존 자료를 먼저 확인했는가?
- 기존 자료가 유효한데 전체 신규 웹조사를 실행하지 않았는가?
- 일부 불완전한 경우 누락·오류 항목만 제한적으로 재검증했는가?
- 입력 원본과 정규화 출력을 구분했는가?
- 기존에 확인된 사실과 근거를 임의로 삭제하지 않았는가?

### 범위

- 리서치 단계에서 최종 분류를 수행하지 않았는가?
- 200개 전체의 공통점이나 YOVIA 적용 결론을 미리 작성하지 않았는가?
- 후속 Skill이 사용할 수 있을 만큼 원시 관찰 정보가 충분한가?
- 원본 입력과 기존 승인 파일을 삭제하거나 이동하지 않았는가?

검사에 실패하면 완료로 보고하지 않는다. 수정 가능한 문제는 바로 수정하고 다시 검사한다. 외부 확인이 필요한 문제는 `partial` 또는 `failed`로 명시한다.

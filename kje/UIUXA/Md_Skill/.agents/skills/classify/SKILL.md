# YOVIA 브랜드 레퍼런스 분류

## 목적

리서치 Skill이 생성한 YOVIA 브랜드 레퍼런스 데이터베이스를 읽고, 현재 Phase의 누적 유효 레코드 전체를 기반으로 공통 디자인 패턴을 먼저 확인한 뒤 분류 기준이 될 대표 디자인 콘셉트를 선정한다. 이후 모든 유효 레코드를 제품 관련성과 선정 콘셉트 적합도라는 두 축으로 분류하여 후속 분석 Skill이 일관된 기준으로 비교할 수 있게 한다.

이 Skill은 다음을 수행한다.

- 리서치 결과의 실제 레코드 수와 상태를 확인한다.
- 동일 공식 도메인의 중복 레코드를 식별한다.
- 분석 가능한 유효 레코드와 제외·보류 레코드를 구분한다.
- 유효 레코드 전체를 대상으로 공통 디자인 요소의 관찰 수와 비율을 계산한다.
- 현재 누적 유효 레코드 전체의 공통점에서 3~5개의 디자인 콘셉트 후보를 도출한다.
- 사용자가 선호하는 콘셉트가 있으면 이를 우선 반영하고, 없으면 근거 기반으로 가장 적합한 콘셉트를 선정한다.
- 각 유효 레코드를 직접·인접·주변 레퍼런스 중 하나로 분류한다.
- 각 유효 레코드를 선정 디자인 콘셉트의 핵심군·보조군·요소 참고군·비적합군 중 하나로 분류한다.
- 세부 카테고리와 보조 태그를 부여한다.
- 모든 분류에 원본 근거와 판단 이유를 기록한다.
- 분류 신뢰도를 표시한다.
- 목적별 우선 검토군을 선정한다.
- 분석 Skill이 읽을 수 있는 분류 결과 MD를 저장한다.

이 Skill은 다음을 수행하지 않는다.

- 새로운 브랜드나 리서치 사실을 조사·추가하지 않는다.
- 선택된 디자인 콘셉트를 최종 웹사이트 설계안이나 와이어프레임으로 확정하지 않는다.
- 전체 정보 구조, 상세 UI 사양, 개발 코드까지 제안하지 않는다.
- 트래픽·전환율·매출 성과를 근거 없이 추정하지 않는다.
- 분류 결과를 근거로 최종 사업 결론을 내리지 않는다.
- 리서치 원본을 수정·삭제·이동하지 않는다.
- 1팀 창의적 결론 → 2팀 직관적 결론 → 통합 결론 최종 보고를 수행하지 않는다.

이 단계의 공통점 분석은 **분류 기준과 디자인 콘셉트를 선정하기 위한 제한된 분석**이다. 패턴의 최종 해석, YOVIA 적용 우선순위, 위험 분석과 최종 UX/UI 제안은 분석 Skill이 담당한다. 최종 보고는 모든 단계 완료 후 `AGENTS.md`의 규칙에 따라 한 번만 진행한다.

## 경로 원칙

1. 프로젝트 루트의 `AGENTS.md`를 먼저 읽는다.
2. `AGENTS.md`에 지정된 입력·출력·아카이브 경로를 우선 적용한다.
3. 별도 경로가 지정되지 않았으면 다음 기본 경로를 사용한다.

```text
입력:
output/01_research/YOVIA_BRAND_REFERENCE_RESEARCH_200.md

출력:
output/02_classification/YOVIA_REFERENCE_CLASSIFICATION.md
```

4. 입력 리서치 파일은 읽기 전용으로 취급한다.
5. 기존 분류 결과의 보존과 실패 결과물의 이동은 `AGENTS.md`의 아카이브 규칙을 따른다.
6. 동일 이름의 기존 결과를 확인하지 않고 덮어쓰지 않는다.
7. 결과 문서에는 프로젝트 루트 기준 상대경로를 기록한다.
8. Windows 절대경로를 문서 본문에 반복해서 넣지 않는다.

## 선행 조건

분류 시작 전 다음을 확인한다.

- 리서치 결과 파일이 실제로 존재하는가?
- 파일의 머리말에 조사 대상 수가 기록되어 있는가?
- 실제 레코드 수와 머리말의 수가 일치하는가?
- 모든 레코드에 ID, 브랜드명, 최종 URL, URL 상태, 조사 상태가 있는가?
- ID가 중복되거나 누락되지 않았는가?
- `active`, `redirected`, `dead` 상태를 식별할 수 있는가?
- `completed`, `partial`, `failed` 상태를 식별할 수 있는가?

필수 입력이 없거나 구조가 심하게 손상되어 있으면 분류하지 않는다. 누락된 파일 또는 구조 문제를 보고하고 멈춘다.

일부 레코드만 불완전하면 전체 작업을 중단하지 않고 해당 레코드를 `보류` 또는 `제외`로 기록한다.

## 입력으로 사용하는 필드

각 레코드에서 다음 필드를 읽는다.

### 식별과 상태

- 레코드 ID
- 브랜드명
- 발견 URL
- 최종 URL
- URL 상태
- 조사 상태
- 확인 수준

### 제품과 사용자 맥락

- 제품·서비스
- 주요 제품 카테고리
- 관찰된 타깃
- 관찰된 사용 상황
- 핵심 메시지·대표 카피

### 웹사이트 참고 요소

- 글로벌 내비게이션
- 히어로 구성
- 제품 목록 탐색 방식
- 제품 상세 정보 순서
- CTA 종류·위치
- 제품·패키지 이미지
- 제품군 구분 방식
- 제품 구조 설명 방식
- 사용 방법 설명 방식
- 숫자·배지·아이콘 사용
- 모바일 콘텐츠 흐름
- 객관적 연구 메모

분류 판단은 원본 리서치에 적힌 사실만 사용한다. 리서치에 없는 제품 특성이나 사용자 맥락을 기억이나 추측으로 추가하지 않는다.

## 현재 누적 유효 레코드 기반 공통 디자인 분석

분류를 시작하기 전에 유효 레코드 전체에서 반복되는 디자인 요소를 집계한다.

### 분석 범위

다음 항목을 레코드별로 동일한 기준으로 확인한다.

- 히어로의 제품·패키지 중심 여부
- 한 문장 가치 제안 사용 여부
- 핵심 수치·배지 사용 여부
- 맛·제품군 컬러 코딩 여부
- 제품 카드·그리드·필터 구조
- 제품 질감·원료·라이프스타일 이미지
- 제품 구조와 사용법 설명 방식
- CTA 종류와 위치
- 판매처 찾기·구매·구독 경로
- 탭·필터·아코디언
- 모바일 햄버거·드로어 메뉴
- 모바일 1열·세로형 콘텐츠 흐름
- 고정 CTA
- 스크롤 모션·이미지 전환
- 여백·타이포그래피·전체 무드

### 집계 규칙

패턴마다 다음 값을 기록한다.

```text
포함 기준
제외 기준
포함 ID 전체
제외 ID 전체
미확인 ID 전체
관찰 레코드 수
확인 가능한 레코드 수
비율
대표 출처 ID
예외 출처 ID
주로 나타나는 제품군
```

비율:

```text
관찰 레코드 수 ÷ 해당 필드가 확인된 유효 레코드 수 × 100
```

규칙:

- 전체 200개라는 파일명만 보고 200개 모두 확인된 것으로 간주하지 않는다.
- `dead`, `failed`, 중복 비대표 레코드는 빈도에서 제외한다.
- `partial`은 해당 필드가 실제 확인된 경우에만 분모와 분자에 반영한다.
- 한 레코드는 동일 패턴에서 한 번만 센다.
- 정확한 집계가 불가능하면 수치를 추정하지 않고 `정확한 집계 불가`라고 기록한다.
- 최소 3개 이상의 서로 다른 유효 레코드에서 반복되어야 공통 패턴 후보로 다룬다.
- 2개는 반복 신호, 1개는 예외·개별 사례로 기록한다.
- 공통점 분석 결과는 디자인 콘셉트 후보와 분류 기준을 만들기 위한 근거로만 사용한다.

### 패턴 독립 집계 검증

- 각 패턴은 다른 패턴이나 이전 분류 문서의 수치를 복사하지 않고 현재 리서치의 실제 관찰에서 독립적으로 집계한다.
- 패턴명은 포함 기준의 범위와 정확히 일치해야 한다. 넓은 패턴명을 유지하면 그 범위에 해당하는 관찰을 임의로 제외하지 않는다.
- 특정 관찰을 제외하려면 제외 기준에서 정보 유형을 먼저 한정한다. 제품 수치만 집계한다면 회사 연혁·가맹점 수 같은 사업 수치를 제외한다고 명시한다.
- 포함·제외·미확인 ID 집합은 서로 겹치지 않아야 하며 합집합은 해당 패턴의 전체 판정 대상 ID와 같아야 한다.
- 포함 ID 개수는 `관찰 레코드 수`와 정확히 같아야 한다.
- `관찰 레코드 수 ≤ 확인 가능한 레코드 수 ≤ 유효 분류 대상 수`가 성립해야 한다.
- 비율은 실제 분자·분모로 다시 계산하고 반올림 자릿수를 문서 안에서 일관되게 사용한다.
- 대표 출처 ID는 반드시 포함 ID에 있어야 한다.
- 예외 출처 ID는 제외 또는 미확인 ID에 있어야 하며 포함 ID와 겹치지 않아야 한다.
- 정적 목록과 인터랙티브 필터처럼 깊이가 다른 관찰을 같은 상위 패턴으로 묶으면 그 차이를 집계 한계에 기록한다.

## 디자인 콘셉트 후보 도출

공통 디자인 패턴을 단순 나열하지 말고 서로 결합 가능한 요소를 묶어 3~5개의 디자인 콘셉트 후보로 만든다.

각 후보는 다음 형식으로 작성한다.

```md
### 콘셉트 후보명

- **핵심 키워드**: ...
- **대표 디자인 요소**: ...
- **근거 패턴**: 관찰 수·비율
- **대표 출처**: [ID] 브랜드명
- **YOVIA 연결점**: ...
- **강점**: ...
- **위험**: ...
- **모바일 적합성**: 높음 / 중간 / 낮음
- **구현 난이도**: 높음 / 중간 / 낮음
```

콘셉트 후보 예시 유형:

- 제품 구조가 선명한 기능 중심형
- 질감과 원료를 강조한 프리미엄 내추럴형
- 맛별 컬러와 패키지를 강조한 비비드 제품형
- 출근·등교·운동 상황을 강조한 라이프스타일형
- 영양 수치와 기능을 강조한 퍼포먼스형

예시 이름을 그대로 강제하지 않는다. 현재 누적 유효 레코드 전체에서 반복 확인된 요소로 후보명을 만든다.

## 선호 디자인 콘셉트 선정

### 사용자 선호 우선

사용자가 마음에 드는 브랜드, 화면, 분위기 또는 콘셉트를 명시했다면 그 선호를 최우선 입력으로 사용한다.

예:

```text
Noosa처럼 질감이 잘 보이는 디자인
Olipop처럼 맛별 컬러가 강한 디자인
Fage처럼 절제되고 신뢰감 있는 디자인
Oats Overnight처럼 기능과 사용법이 선명한 디자인
```

사용자 선호가 공통 패턴과 충돌하더라도 무시하지 않는다. 다만 구현 위험, 모바일 적합성, YOVIA 핵심 제품 경험과의 충돌 여부를 함께 기록한다.

### 사용자 선호가 없는 경우

다음 기준으로 콘셉트 후보를 비교하고 가장 적합한 하나를 `선정 디자인 콘셉트`로 추천한다.

| 기준 | 판단 내용 |
|---|---|
| YOVIA 핵심 적합성 | 파우치·내장 스푼·토핑을 설명하기 적합한가 |
| 현재 누적 근거 강도 | 여러 유효 레코드에서 반복되는가 |
| 제품 이해도 | 무엇이 들어 있고 어떻게 먹는지 빠르게 전달하는가 |
| 디자인 차별성 | 일반 요거트 사이트와 구별되는가 |
| 모바일 확장성 | 모바일 1열과 터치 UX로 변환 가능한가 |
| 구현 가능성 | 현재 범위와 자원에서 구현 가능한가 |
| 유지 가능성 | 맛·제품이 늘어도 체계를 유지할 수 있는가 |

평가 결과는 `높음 / 중간 / 낮음`으로 작성하고 한 문장 이상의 이유를 붙인다. 근거 없이 취향만으로 선정하지 않는다.

### 최종 선정 규칙

- 기본적으로 주 콘셉트 하나만 선정한다.
- 필요한 경우 보조 콘셉트 하나를 지정할 수 있다.
- 주 콘셉트와 보조 콘셉트의 역할이 겹치지 않게 한다.
- 선정 이유, 대표 출처, 제외한 후보의 이유를 기록한다.
- 사용자가 직접 선택한 경우 `사용자 선택`으로 표시한다.
- 모델이 추천한 경우 `근거 기반 추천`으로 표시한다.
- 선택된 콘셉트는 분석 단계에서 검토 가능한 가설이며 최종 디자인 확정안이 아니다.

## 디자인 콘셉트 기반 분류

제품 관련성 분류와 별도로, 모든 유효 레코드를 선정 디자인 콘셉트와의 적합도에 따라 분류한다.

### A. 핵심 디자인 레퍼런스

선정 콘셉트의 핵심 요소가 여러 항목에서 강하게 나타나는 레코드다.

기본 조건:

- 최소 3개 이상의 핵심 디자인 요소가 확인됨
- 히어로·컬러·이미지·타이포그래피·제품 탐색 중 복수 영역이 일치함
- YOVIA 적용 시 구조를 직접 참고할 수 있음

### B. 보조 디자인 레퍼런스

선정 콘셉트와 전반적으로 어울리지만 일부 요소만 강하게 일치하는 레코드다.

기본 조건:

- 최소 2개 이상의 핵심 디자인 요소가 확인됨
- 전체 구조보다 특정 섹션이나 표현 방식이 유용함

### C. 요소 참고 레퍼런스

전체 콘셉트는 다르지만 한 가지 디자인 요소를 참고할 가치가 있는 레코드다.

예:

- 맛별 컬러
- 제품 질감 이미지
- 단계별 사용법
- 모바일 CTA
- 제품 카드
- FAQ 아코디언

### D. 비적합·반면교사

선정 콘셉트와 방향이 다르거나 YOVIA에 적용할 경우 위험이 큰 레코드다.

예:

- 제품보다 모션이 우선됨
- 정보가 과도하게 숨겨짐
- 모바일 축소 대응만 존재함
- 브랜드 감성은 강하지만 제품 구조가 보이지 않음
- 확인되지 않은 수치가 장식처럼 사용됨

비적합 레코드도 삭제하지 않고 어떤 점을 피해야 하는지 기록한다.

## 이중 분류 원칙

모든 유효 레코드는 다음 두 축을 함께 가진다.

```text
1축 — 제품 관련성:
직접 / 인접 / 주변

2축 — 선정 디자인 콘셉트 적합도:
핵심 / 보조 / 요소 참고 / 비적합
```

예:

```text
[015] GoGo SqueeZ
- 제품 관련성: 직접
- 디자인 적합도: 보조
```

```text
[051] Olipop
- 제품 관련성: 인접
- 디자인 적합도: 핵심
```

제품 카테고리가 멀어도 선정 콘셉트와 디자인 적합도가 높을 수 있다. 반대로 직접 레퍼런스라도 디자인 방향이 맞지 않으면 요소 참고 또는 비적합으로 분류할 수 있다.

## 분류 전 상태 정리

분류 전에 다음 수치를 계산한다.

```text
전체 레코드 수
active 수
redirected 수
dead 수
completed 수
partial 수
failed 수
중복 공식 도메인 후보 수
유효 분류 대상 수
제외 수
보류 수
```

### 유효 분류 대상

기본적으로 다음 조건을 만족하는 레코드다.

- URL 상태가 `active` 또는 `redirected`
- 조사 상태가 `completed` 또는 `partial`
- 공식 사이트 또는 최종 공식 도메인이 확인됨
- 분류에 필요한 제품 카테고리나 사용 상황이 최소한 하나 이상 확인됨

### 제외

다음 중 하나에 해당하면 분류 집계에서 제외한다.

- URL 상태가 `dead`
- 조사 상태가 `failed`
- 공식 사이트 확인에 실패함
- 동일 공식 도메인의 중복 레코드로 대표값이 아님

제외 레코드는 삭제하지 않는다. ID, 브랜드명, 제외 유형, 근거, 대표 레코드 ID를 별도 표에 기록한다.

### 보류

다음과 같은 경우 `보류`로 기록한다.

- 공식 사이트는 확인했지만 제품 카테고리가 불명확함
- `partial` 상태이고 분류 근거가 부족함
- 서로 다른 분류 기준이 비슷한 강도로 충돌함
- 공식 도메인 관계가 불분명함
- 원본 리서치 내용끼리 모순됨

보류 레코드를 억지로 직접·인접·주변 중 하나에 넣지 않는다.

## 동일 공식 도메인 처리

1. 최종 URL의 호스트명을 정규화하여 동일 공식 도메인을 찾는다.
2. `www.` 유무, 프로토콜, 마지막 슬래시는 동일성 판단에서 제외한다.
3. 국가별 공식 사이트나 브랜드별 독립 하위 도메인은 제품·콘텐츠가 실질적으로 다르면 별도 레코드로 유지할 수 있다.
4. 동일 공식 도메인이 중복되면 첫 번째 유효 레코드를 기본 대표값으로 사용한다.
5. 첫 번째 레코드가 `partial`이고 뒤의 레코드가 `completed`라면 더 완전한 레코드를 대표값으로 사용할 수 있다.
6. 대표값을 바꿨다면 이유를 기록한다.
7. 중복 레코드는 `제외·중복` 표에 대표 레코드 ID와 함께 남긴다.
8. 중복을 조용히 삭제하거나 ID를 다시 매기지 않는다.

## 3대 분류 체계

각 유효 레코드에는 **주 분류 하나만** 부여한다.

### 1. 직접 레퍼런스

YOVIA의 제품 카테고리 또는 핵심 사용 경험과 직접적으로 겹치는 레퍼런스다.

다음 중 하나 이상이 핵심 제품·서비스 또는 핵심 사용 상황으로 확인되어야 한다.

- 요거트
- 그릭요거트
- 스키르
- 마시는 요거트
- 요거트 파우치
- 식품 파우치
- 휴대형 식사
- 이동 중 섭취
- 간편 아침 식사
- 개봉·혼합·섭취 과정이 YOVIA와 직접 유사한 제품
- 제품 용기 안에서 내용물과 토핑을 결합하는 구조

단순히 웰니스 브랜드이거나 식품 브랜드라는 이유만으로 직접 레퍼런스로 분류하지 않는다.

### 2. 인접 레퍼런스

제품 카테고리는 동일하지 않지만 YOVIA의 기능, 사용 상황, 구매 방식 또는 정보 전달 문제와 밀접한 레퍼런스다.

예:

- 단백질 음료·바
- 식사 대용식
- 기능성 식품
- 오트밀·시리얼 기반 간편 아침
- 스무디·분말·믹스형 간편식
- DTC 식품
- 구독형 식품
- 준비 단계가 명확한 소비재
- 영양 수치·기능 작동 원리를 핵심으로 설명하는 제품
- 이동·통근·학교·운동 상황을 중심으로 하는 식품

제품 카테고리보다 사용 상황이나 기능 설명 방식이 YOVIA와 가까운 경우 인접 레퍼런스로 분류한다.

### 3. 주변 레퍼런스

제품 카테고리와 사용 상황은 상대적으로 멀지만 웹사이트 설계 일부를 참고할 가치가 있는 레퍼런스다.

예:

- 패키지 컬러 코딩이 명확한 브랜드
- 제품 탐색·필터·카드 구조가 우수한 사이트
- 복잡한 기능을 직관적으로 설명하는 소비재 사이트
- 맛·향·원료를 시각적으로 구분하는 브랜드
- 브랜드 스토리나 이미지 연출을 참고할 수 있는 사이트
- CTA, 구독, 판매처 찾기, 모바일 탐색 구조만 참고할 수 있는 사이트

브랜드가 시각적으로 아름답다는 이유만으로 포함하지 않는다. YOVIA가 참고할 수 있는 구체적인 웹사이트 요소가 확인되어야 한다.

## 분류 우선순위 규칙

한 레코드가 여러 분류에 해당할 수 있을 때 다음 순서로 판단한다.

```text
제품 카테고리 직접성
→ 사용 상황 직접성
→ 제품 구조·사용법 유사성
→ 기능·영양 정보 유사성
→ 구매·탐색 UX 유사성
→ 시각·브랜딩 참고성
```

판정 원칙:

- 제품 또는 핵심 사용 경험이 YOVIA와 직접 겹치면 `직접`을 우선한다.
- 제품은 다르지만 사용 상황과 기능 설명이 강하게 겹치면 `인접`으로 분류한다.
- 시각·탐색·브랜딩 요소만 참고할 수 있으면 `주변`으로 분류한다.
- 복수 특성을 보존하기 위해 주 분류 외에 보조 태그를 사용한다.
- 애매한 경우 임의 선택하지 않고 신뢰도 `낮음` 또는 `보류`로 기록한다.

- `기타`는 가능한 한 피하고, 사용한 경우 구체적인 설명을 덧붙인다.

## 분류 신뢰도

각 주 분류에 신뢰도를 기록한다.

### 높음

- 제품 카테고리 또는 핵심 사용 상황이 분류 정의와 직접 일치함
- 근거가 복수 필드 또는 복수 확인 페이지에 존재함
- 상충되는 정보가 없음

### 중간

- 분류 근거는 분명하지만 한두 필드에만 존재함
- `partial` 레코드이거나 일부 정보가 제한됨
- 다른 분류의 특징도 함께 나타남

### 낮음

- 분류 근거가 제한적임
- 원본 리서치에 모호하거나 상충되는 표현이 있음
- 주변 참고 요소만 일부 확인됨
- 추가 확인이 필요함

신뢰도가 낮고 주 분류 결정이 어려우면 `보류`가 우선이다.

## 분류 근거 작성

각 레코드에는 다음 내용을 기록한다.

```text
주 분류
분류 신뢰도
세부 카테고리
보조 태그
분류 근거
대표 근거 필드
```

분류 근거는 한 문장 이상으로 작성한다.

좋은 예:

```text
파우치형 식품을 이동 중 바로 섭취하는 사용 상황과 개봉 편의성이 핵심 제품 경험으로 확인되어 직접 레퍼런스로 분류했다.
```

나쁜 예:

```text
YOVIA와 비슷함.
```

대표 근거 필드는 다음과 같이 원본 위치를 표시한다.

```text
[브랜드·제품 관찰/제품·서비스]
[브랜드·제품 관찰/관찰된 사용 상황]
[제품 설명 관찰/사용 방법 설명 방식]
```

## 목적별 우선 검토군

분류 완료 후, 후속 분석에서 먼저 검토할 레퍼런스를 다음 목적별로 선정한다.

### A. 제품·브랜드 표현

- 요거트·식품의 질감
- 패키지
- 원료·영양 신뢰
- 제품군 구분
- 브랜드 보이스

### B. 파우치·휴대 경험

- 파우치 구조
- 개봉 방식
- 휴대성
- 이동 중 섭취
- 제품 사용 단계
- 내장 도구 또는 복합 패키지

### C. 간편 아침·기능성 식품 UX

- 아침·통근·등교·운동 상황
- 영양 수치
- 기능 설명
- 제품 비교
- 구독·구매 흐름

### D. 탐색·모바일·커머스 UX

- 제품 카드
- 필터·탭
- 맛별 탐색
- 모바일 1열
- 고정 CTA
- 판매처 찾기
- FAQ·아코디언

선정 규칙:

- 각 목적별 기본 5~15개를 선정한다.
- 실제 유효 레코드 수가 적으면 억지로 수를 채우지 않는다.
- 선정 이유를 한 문장으로 쓴다.
- 동일 레코드는 여러 목적군에 포함될 수 있다.
- 이 단계에서는 “최고”, “성과가 좋다”라고 단정하지 않는다.
- 원본 리서치의 확인 수준과 분류 신뢰도가 높은 레코드를 우선한다.

## 현재 시안 보완용 역할 분류

부족점 직접 보완 모드의 사례는 기존 제품 관련성·디자인 적합도 분류를 대체하지 않고, 현재 시안에서 맡는 역할을 추가로 하나만 부여한다.

| 역할 | 확인 범위 | 선택 기준 |
|---|---|---|
| 사용성 | 상품 정보 순서, 제품 탐색·비교, 다음 행동 흐름 | 현재 정보 구조의 불일치를 직접 해결하는가 |
| 심미성 | 제품·패키지 크기, 반복 그래픽, 카드·여백·제목 위계 | 기존 시각 방향을 유지하면서 약해진 구간을 보완하는가 |
| 무드 | 일상 문제, 선택 이유, 문장과 장면의 분위기 | 제품 주장보다 사용자의 하루를 먼저 이해시키는가 |

분류 규칙:

- 한 사례에 여러 역할을 중복 부여하지 않는다. 가장 직접적으로 해결하는 핵심 문제 하나를 선택한다.
- 사례 전체를 좋은 디자인으로 평가하지 않고, 선택한 역할에 필요한 확인 구간만 사용한다.
- `선택 이유`와 `보완할 현재 구간`을 반드시 연결한다.
- 내부 시안은 `내부 시안`으로, 외부 공식 페이지는 확인한 URL과 근거 페이지로 구분한다.
- YOVIA에 적용하지 않을 색상·문장·상품 주장·기능·정책을 `제외 요소`로 기록한다.

보완용 분류표는 다음 필드를 사용한다.

```md
| 역할 | 레퍼런스와 확인 위치 | 선택 이유 | 보완할 현재 구간 | 제외 요소 |
|---|---|---|---|---|
```

이 표는 현재 부족점 해결을 위한 제한적 선택 기록이며, 전체 레퍼런스의 공통 패턴 빈도나 선정 콘셉트 집계를 대신하지 않는다.

## 분류 출력 데이터 계약

분석 Skill이 필드명을 안정적으로 읽을 수 있도록 다음 항목명을 고정한다.

```text
공통 디자인 패턴 집계
디자인 콘셉트 후보
선정 디자인 콘셉트
선정 방식
주 콘셉트 역할
보조 콘셉트 역할
제품 관련성
제품 관련성 근거
제품 관련성 신뢰도
디자인 적합도
디자인 적합도 근거
디자인 적합도 신뢰도
세부 카테고리
보조 태그
보류·제외·중복
목적별 우선 검토군
선정 디자인 콘셉트 구현 참고군
```

허용 값:

```text
선정 방식:
사용자 선택 / 근거 기반 추천

제품 관련성:
직접 / 인접 / 주변

디자인 적합도:
핵심 / 보조 / 요소 참고 / 비적합
```

`주 분류`, `관련군`, `우수군`처럼 해석이 달라질 수 있는 임의 필드명으로 대체하지 않는다.

공통 디자인 패턴 집계에는 다음 값을 반드시 포함한다.

```text
패턴명
관찰 레코드 수
확인 가능한 레코드 수
비율
대표 출처 ID
예외 출처 ID
주요 출현 제품군
집계 한계
```

각 패턴에는 위 값과 함께 `포함 기준`, `제외 기준`, `포함 ID 전체`, `제외 ID 전체`, `미확인 ID 전체`를 반드시 저장한다. 분석 Skill은 이 전체 ID 목록으로 분자와 출처를 검증한다.

## 분류 절차

1. `AGENTS.md`와 입력 리서치 파일을 읽는다.
2. 실제 레코드 수와 상태 집계를 계산한다.
3. 동일 공식 도메인 중복 후보를 식별한다.
4. 대표 레코드와 중복 제외 레코드를 확정한다.
5. `dead`, `failed`, 공식성 미확인 레코드를 제외한다.
6. 정보가 부족하거나 충돌하는 레코드를 보류한다.
7. 유효 레코드 전체의 공통 디자인 요소를 동일 기준으로 집계한다.
8. 공통 패턴의 관찰 수·분모·비율·대표 출처·예외를 기록한다.
9. 공통 패턴을 결합하여 3~5개의 디자인 콘셉트 후보를 만든다.
10. 사용자 선호가 있으면 이를 우선 반영하고, 없으면 근거 기반 평가로 주 콘셉트를 선정한다.
11. 주 콘셉트와 필요한 경우 보조 콘셉트의 선정 이유를 기록한다.
12. 유효 레코드마다 제품·사용 상황·제품 구조·웹 참고 요소를 추출한다.
13. 제품 관련성 기준으로 직접·인접·주변 주 분류 하나를 결정한다.
14. 선정 콘셉트 적합도 기준으로 핵심·보조·요소 참고·비적합 중 하나를 결정한다.
15. 두 분류의 신뢰도와 한 문장 이상의 근거를 작성한다.
16. 세부 카테고리와 보조 태그를 부여한다.
17. 직접·인접·주변·보류·제외 수를 집계한다.
18. 핵심·보조·요소 참고·비적합 수를 집계한다.
19. 목적별 우선 검토군을 선정한다.
20. 모든 유효 레코드 ID가 두 분류 축에서 각각 정확히 한 번 분류되었는지 검사한다.
21. 분류 결과 MD를 저장한다.
22. 완료 전 품질 검사를 수행한다.

## 수량 검증

다음 관계가 모두 성립해야 한다.

```text
직접 + 인접 + 주변 = 유효 분류 대상

핵심 디자인군 + 보조 디자인군 + 요소 참고군 + 비적합군 = 유효 분류 대상

유효 분류 대상 + 보류 + 제외·중복 = 전체 레코드
```

단, 동일 레코드가 여러 목적별 우선 검토군에 포함되는 것은 허용한다.

검증 규칙:

- 모든 유효 레코드는 제품 관련성 축에서 정확히 한 번 분류되어야 한다.
- 모든 유효 레코드는 디자인 적합도 축에서 정확히 한 번 분류되어야 한다.
- 보류와 제외 레코드는 두 유효 분류 집계에 포함하지 않는다.
- 동일 ID를 같은 분류 축에서 중복 기재하지 않는다.
- ID를 임의로 다시 번호 매기지 않는다.
- 실제 수량과 맞지 않으면 결과를 완료로 보고하지 않는다.

## 금지 사항

- 현재 Phase의 일부 우선 브랜드만 분류하고 현재 누적 전체를 분류했다고 작성하는 것
- 제품 카테고리만 보고 사용 상황과 제품 구조를 무시하는 것
- 시각적으로 예쁘다는 이유만으로 주변 레퍼런스에 포함하는 것
- `dead` 또는 `failed`를 유효 분류 대상으로 사용하는 것
- `partial` 레코드의 미확인 필드를 추측으로 채우는 것
- 동일 공식 도메인을 별도 사례로 중복 집계하는 것
- 한 레코드에 직접·인접·주변 주 분류를 동시에 부여하는 것
- 분류 근거 없이 브랜드명만 나열하는 것
- 원본 리서치에 없는 브랜드·제품·기능을 생성하는 것
- 현재 누적 유효 레코드 전체를 집계하지 않고 일부 우선 브랜드만으로 공통 디자인 패턴을 확정하는 것
- 선정 디자인 콘셉트를 곧바로 최종 화면 설계·와이어프레임·개발 사양으로 확정하는 것
- 분석 결과 예시 파일의 결론을 분류 근거처럼 복사하는 것
- 사용자의 디자인 선호를 무시하고 모델 취향만으로 콘셉트를 선정하는 것
- 근거 패턴·대표 출처·위험 설명 없이 “가장 예쁜 콘셉트”라고 선정하는 것
- 제품 관련성 분류와 디자인 적합도 분류를 하나의 기준처럼 섞는 것
- 직접 레퍼런스라는 이유만으로 디자인 핵심군에 자동 포함하는 것
- 주변 레퍼런스라는 이유만으로 디자인 참고 가치가 낮다고 판단하는 것
- 원본 리서치 파일을 수정하거나 삭제하는 것

## 완료 전 품질 검사

### 입력 무결성

- 리서치 파일이 존재하는가?
- 실제 레코드 수를 계산했는가?
- ID와 상태 필드를 확인했는가?
- 원본 리서치의 버전을 기록했는가?

### 상태·중복 처리

- `active`, `redirected`, `dead`를 구분했는가?
- `completed`, `partial`, `failed`를 구분했는가?
- 동일 공식 도메인을 식별했는가?
- 대표 레코드 선정 이유가 필요한 경우 기록했는가?
- 제외·중복 레코드를 삭제하지 않고 별도 표에 남겼는가?

### 공통점·콘셉트 선정

- 공통 디자인 패턴이 실제 유효 레코드 전체를 기반으로 집계되었는가?
- 패턴마다 관찰 수·분모·비율 또는 집계 불가 사유가 있는가?
- 디자인 콘셉트 후보가 실제 반복 패턴을 조합해 만들어졌는가?
- 사용자 선호가 있으면 정확히 반영했는가?
- 사용자 선호가 없으면 선정 기준과 이유를 기록했는가?
- 선정 콘셉트에 대표 출처와 위험이 연결되는가?
- 선정 콘셉트를 최종 디자인 확정안처럼 표현하지 않았는가?
- 각 패턴에 포함·제외 기준과 포함·제외·미확인 ID 전체가 있는가?
- 각 패턴의 포함 ID 수와 관찰 레코드 수가 정확히 같은가?
- 관찰 레코드 수가 확인 가능한 레코드 수보다 크지 않은가?
- 포함·제외·미확인 ID가 중복 없이 전체 판정 대상을 덮는가?
- 비율을 실제 분자·분모로 다시 계산했을 때 표기값과 일치하는가?
- 대표 출처가 포함 ID에, 예외 출처가 제외 또는 미확인 ID에 있는가?
- 패턴명·포함 기준·포함 ID·분자 사이에 의미 모순이 없는가?
- 이전 분류 파일의 수치를 검증 없이 복사하지 않고 현재 리서치에서 다시 집계했는가?

### 분류 정확성

- 모든 유효 레코드가 제품 관련성 축에서 정확히 한 번 분류되었는가?
- 모든 유효 레코드가 디자인 적합도 축에서 정확히 한 번 분류되었는가?
- 직접·인접·주변 정의를 일관되게 적용했는가?
- 핵심·보조·요소 참고·비적합 정의를 일관되게 적용했는가?
- 각 레코드에 두 분류의 근거가 있는가?
- 신뢰도와 근거가 서로 일치하는가?
- 애매한 레코드를 보류했는가?
- 세부 카테고리와 태그가 원본 근거에 기반하는가?
- 요약표와 레코드별 상세의 제품 관련성·신뢰도·디자인 적합도·신뢰도가 ID별로 일치하는가?
- 각 보조 태그와 핵심 디자인 근거를 원본 리서치의 실제 문장과 P 번호로 추적할 수 있는가?
- 리서치에서 확인되지 않은 판매처·구매·구독 CTA를 태그나 패턴 근거로 확장하지 않았는가?

### 수량

- 직접 + 인접 + 주변이 유효 분류 대상과 같은가?
- 핵심 + 보조 + 요소 참고 + 비적합이 유효 분류 대상과 같은가?
- 유효 + 보류 + 제외·중복이 전체 레코드와 같은가?
- 표의 행 수와 요약 수가 일치하는가?
- 중복 ID나 미분류 ID가 없는가?
- 제품 관련성 축의 ID 집합과 디자인 적합도 축의 ID 집합이 유효 ID 전체와 각각 정확히 같은가?
- 각 축에서 동일 ID가 정확히 한 번만 나타나는가?
- 표의 분류값과 상세 섹션의 분류값이 서로 같은가?

### 분석 데이터 계약

- 고정 출력 필드명이 모두 존재하는가?
- 공통 디자인 집계에 관찰 수·확인 분모·비율·출처·한계가 있는가?
- 제품 관련성과 디자인 적합도의 근거·신뢰도가 분리되어 있는가?
- 선정 방식이 `사용자 선택` 또는 `근거 기반 추천`으로 기록되었는가?
- 분석 Skill이 재사용할 수 있도록 집계값이 표준 형식으로 저장되었는가?

### 단계 분리

- 공통점 분석이 디자인 콘셉트와 분류 기준 선정 범위에 한정되었는가?
- 전체 정보 구조·상세 화면·최종 적용 우선순위까지 확정하지 않았는가?
- 분석 Skill이 사용할 공통 패턴·선정 콘셉트·이중 분류·우선 검토군을 제공했는가?
- 최종 1팀 창의적 결론 → 2팀 직관적 결론 → 통합 결론 보고를 수행하지 않았는가?

검사 실패 시 완료로 보고하지 않는다. 수정 가능한 문제는 수정한 뒤 다시 검사하고, 외부 확인이 필요한 항목은 보류 또는 추가 확인으로 기록한다.

## 완료 보고

### 단일 classify 단계만 요청한 경우

다음 내용만 간단히 보고한다.

- 생성 또는 갱신한 분류 파일 경로
- 전체 레코드 수와 유효 분류 대상 수
- 현재 누적 유효 레코드 기반 핵심 공통 디자인 패턴 3개 이내
- 선정 디자인 콘셉트와 선정 방식
- 직접·인접·주변·보류·제외 수
- 디자인 핵심·보조·요소 참고·비적합 수
- 중복 공식 도메인 처리 수
- 신뢰도 낮음 또는 추가 확인이 필요한 핵심 항목
- 다음 단계가 분석 Skill임을 알리는 한 줄

### 전체 실행인 경우

사용자에게 단계별 완료 보고를 하지 않는다. 내부 검증 결과만 유지하고 통과하면 analyze 단계로 이동한다.

최종 `1팀 창의적 결론 → 2팀 직관적 결론 → 통합 결론` 보고는 수행하지 않는다. 일반 전체 실행 또는 Phase 3의 리서치·분류·분석이 모두 끝난 뒤 `AGENTS.md`의 규칙에 따라 한 번만 진행한다.

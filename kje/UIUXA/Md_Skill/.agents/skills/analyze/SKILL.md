# YOVIA 레퍼런스 UX/UI 분석

## 목적

리서치 Skill이 생성한 원시 데이터와 분류 Skill이 생성한 공통 디자인 집계·선정 콘셉트·이중 분류 결과를 함께 읽고, YOVIA 웹사이트 기획에 필요한 최종 UX/UI 해석과 적용 방향을 도출한다.

이 Skill은 다음을 수행한다.

- 분석 가능한 전체 레코드 수를 확정한다.
- 분류 단계의 공통 디자인 패턴 집계값을 원본 리서치로 검증한다.
- 검증된 분류 집계값은 중복 계산하지 않고 재사용한다.
- 선정 디자인 콘셉트와 선정 방식이 원본 근거에 부합하는지 검토한다.
- 직접·인접·주변 제품 관련성별 공통점과 차이를 분석한다.
- 핵심·보조·요소 참고·비적합 디자인 적합도별 공통점과 차이를 분석한다.
- 주 콘셉트와 보조 콘셉트가 YOVIA에서 맡을 역할을 분석한다.
- 세부 제품군과 사용 경험별 특화 패턴을 분석한다.
- 대표 사례뿐 아니라 예외·반대 사례·실패 가능성과 대안 콘셉트를 기록한다.
- 관찰된 타사 패턴과 YOVIA 적용 제안을 분리한다.
- 적용 우선순위·구현 난이도·위험·중단 조건을 제시한다.
- 분석 결과를 `YOVIA_RESEARCH_ANALYSIS.md`로 저장한다.

이 Skill은 다음을 수행하지 않는다.

- 새로운 브랜드나 리서치 레코드를 추가하지 않는다.
- 공식 사이트를 처음부터 다시 조사하지 않는다.
- 원본 근거 없이 제품 관련성 또는 디자인 적합도를 임의로 재분류하지 않는다.
- 분류 집계값이 다르다는 이유로 분류 파일을 직접 수정하지 않는다.
- 확인되지 않은 제품 수치, 기능, 인증, 사용자 반응을 생성하지 않는다.
- 최종 와이어프레임·시각 디자인·개발 코드를 제작하지 않는다.
- 1팀 창의적 결론 → 2팀 직관적 결론 → 통합 결론 최종 보고를 수행하지 않는다.

분류 결과와 원본이 충돌하면 `분류 재검토 필요`로 기록한다. 최종 보고는 리서치·분류·분석이 모두 끝난 뒤 `AGENTS.md`의 규칙에 따라 한 번만 진행한다.

## 경로 원칙

1. 프로젝트 루트의 `AGENTS.md`를 먼저 읽는다.
2. `AGENTS.md`에 지정된 입력·출력·아카이브 경로를 우선 적용한다.
3. 경로가 지정되어 있지 않으면 다음 기본 경로를 사용한다.

```text
입력 리서치:
output/01_research/YOVIA_BRAND_REFERENCE_RESEARCH_200.md

입력 분류:
output/02_classification/YOVIA_REFERENCE_CLASSIFICATION.md

출력 분석:
output/03_analysis/YOVIA_RESEARCH_ANALYSIS.md
```

4. 입력 원본을 수정·이동·삭제하지 않는다.
5. 기존 분석 결과의 보존과 실패 결과물의 이동은 `AGENTS.md`의 아카이브 규칙을 따른다.
6. 동일 이름의 기존 분석 파일을 확인하지 않고 덮어쓰지 않는다.
7. 결과 문서에는 프로젝트 루트 기준 상대경로를 기록한다.

## 선행 조건

작업 시작 전에 다음 조건을 확인한다.

- 리서치 결과 파일이 존재하는가?
- 분류 결과 파일이 존재하는가?
- 리서치 결과의 실제 레코드 수가 머리말의 수와 일치하는가?
- 리서치와 분류 파일이 같은 조사 버전을 대상으로 하는가?
- 분류 결과에 모든 유효 레코드 ID가 연결되어 있는가?
- `failed`, `dead`, 중복 비대표, 보류 처리 기준이 명시되어 있는가?
- 제품 관련성 `직접 + 인접 + 주변 = 유효 분류 대상`이 성립하는가?
- 디자인 적합도 `핵심 + 보조 + 요소 참고 + 비적합 = 유효 분류 대상`이 성립하는가?
- 각 유효 ID가 두 분류 축에서 각각 정확히 한 번 분류되었는가?
- 공통 디자인 패턴 집계에 관찰 수·확인 가능 분모·비율·대표 출처가 있는가?
- 디자인 콘셉트 후보와 선정 디자인 콘셉트가 있는가?
- 선정 방식이 `사용자 선택` 또는 `근거 기반 추천`으로 기록되었는가?
- 주 콘셉트와 보조 콘셉트의 역할이 기록되었는가?

필수 입력이 없거나 버전·수량·ID 연결이 일치하지 않으면 분석을 시작하지 않는다. 필요한 파일과 불일치 항목을 보고한다.

## 입력 자료의 역할

### 1. 리서치 결과 MD

다음 사실의 최종 원본 근거로 사용한다.

- 레코드 ID와 브랜드명
- 발견 URL·최종 URL·URL 상태
- 조사 상태
- P1~P5 확인 페이지
- 브랜드·제품 관찰
- 웹 구조 관찰
- 시각 관찰
- 제품 설명 관찰
- 인터랙션·반응형 관찰
- 객관적 연구 메모

리서치 파일에 없는 사실은 분석 결과에 확정적으로 추가하지 않는다.

### 2. 분류 결과 MD

다음 데이터를 읽고 검증·재사용한다.

- 공통 디자인 패턴 집계
- 패턴별 관찰 레코드 수
- 패턴별 확인 가능한 레코드 수
- 패턴별 비율
- 대표·예외 출처 ID
- 디자인 콘셉트 후보 3~5개
- 선정 디자인 콘셉트
- 선정 방식: 사용자 선택 / 근거 기반 추천
- 주 콘셉트 역할
- 보조 콘셉트 역할
- 제품 관련성: 직접 / 인접 / 주변
- 제품 관련성 근거와 신뢰도
- 디자인 적합도: 핵심 / 보조 / 요소 참고 / 비적합
- 디자인 적합도 근거와 신뢰도
- 세부 카테고리와 보조 태그
- 제외·보류 레코드
- 중복 공식 도메인의 대표 레코드
- 목적별 우선 검토군
- 선정 디자인 콘셉트 구현 참고군

분류 결과와 원시 리서치가 충돌하면 임의로 하나를 선택하지 않는다. 해당 항목을 `분류 재검토 필요`로 기록한다.

## 분류 집계 검증·재사용

분류 단계가 이미 계산한 공통 디자인 패턴의 빈도를 분석 단계에서 처음부터 다시 계산하지 않는다.

처리 순서:

```text
분류 MD의 집계값 읽기
→ 원본 리서치에서 분자·분모·출처 표본 검증
→ 수량 공식과 중복 제외 기준 확인
→ 일치하면 같은 값을 재사용
→ 불일치하면 분류 재검토 필요로 기록
```

검증 규칙:

- 동일 도메인 중복 비대표가 분모에서 제외되었는지 확인한다.
- `dead`, `failed`가 유효 집계에서 제외되었는지 확인한다.
- `partial`은 해당 필드가 확인된 경우에만 집계되었는지 확인한다.
- 분류의 관찰 수가 대표 출처 목록과 모순되지 않는지 확인한다.
- 각 핵심 패턴의 `포함 기준`, `제외 기준`, `포함 ID 전체`, `제외 ID 전체`, `미확인 ID 전체`를 먼저 읽는다.
- 포함 ID 전체를 원본 리서치와 대조한다. 대표 출처 몇 개만 표본 확인하고 전체 집계가 검증됐다고 쓰지 않는다.
- 포함 ID 개수와 분자가 같고 `분자 ≤ 확인 가능한 분모 ≤ 유효 대상`인지 다시 계산한다.
- 대표 출처는 포함 ID에, 예외 출처는 제외 또는 미확인 ID에 있는지 확인한다.
- 패턴명과 포함 기준이 실제 포함 ID 판정에 동일하게 적용됐는지 확인한다.
- 모든 집계값을 새 정의로 재산출하지는 않지만 분류가 선언한 기준으로 핵심 패턴 전체 ID와 선정 콘셉트 근거를 대조한다.
- 오류가 없으면 분류의 수치를 그대로 사용한다.
- 오류가 있으면 분석 문서에 수정 전·후 수치를 임의로 병기하지 않고 `분류 재검토 필요`와 오류 근거를 기록한다.
- 하나라도 불일치가 있으면 `분류 재검토 필요 항목: 없음`이라고 기록할 수 없다.
- 분석 표의 패턴명·분자·분모·비율은 검증된 분류 표와 정확히 같아야 한다.
- 분석 단계는 검증된 집계의 의미, 그룹 차이, 적용 방향, 우선순위와 위험을 확장한다.

## 분석 대상 확정

분석 전에 다음 수치를 확인한다.

```text
전체 레코드 수
active 수
redirected 수
dead 수
completed 수
partial 수
failed 수
중복 제외 수
최종 분석 대상 수
직접 레퍼런스 수
인접 레퍼런스 수
주변 레퍼런스 수
디자인 핵심군 수
디자인 보조군 수
요소 참고군 수
비적합군 수
미분류·보류 수
```

기본 분석 대상:

- `URL 상태`가 `active` 또는 `redirected`
- `조사 상태`가 `completed` 또는 `partial`
- 동일 공식 도메인은 분류 결과에서 지정한 대표 레코드만 사용
- `partial`은 확인된 필드만 사용
- `dead` 또는 `failed`는 반복 빈도 계산에서 제외하되 제외 수와 이유는 기록

수량 검증:

```text
직접 + 인접 + 주변 = 최종 분석 대상
핵심 + 보조 + 요소 참고 + 비적합 = 최종 분석 대상
최종 분석 대상 + 보류 + 제외·중복 = 전체 레코드
```

실제 분석 대상이 200개 미만이면 `200개 전체 분석 완료`라고 쓰지 않는다. 반드시 `전체 200개 중 유효 분석 대상 N개`라고 기록한다.

## 분석 단위

다음 여섯 층위로 분석한다.

### 1. 전체 레퍼런스 공통 패턴

분류 단계에서 검증된 전체 집계값을 우선 재사용하고, 다음 구조의 의미와 상호 관계를 분석한다.

- 글로벌 내비게이션과 헤더
- 히어로 영역
- 가치 제안 카피
- 제품·패키지 이미지
- 핵심 수치·배지
- 제품군 탐색
- 제품 상세 정보 순서
- 제품 구조·사용법 전달
- 영양·원료·신뢰 정보
- CTA와 구매·구독·판매처 경로
- 컬러와 타이포그래피
- 라이프스타일·질감·원료 이미지
- 탭·필터·아코디언
- 모바일 메뉴와 콘텐츠 흐름
- 모바일 고정 CTA
- 모션과 이미지 전환
- FAQ·리뷰·브랜드 스토리

### 2. 제품 관련성별 공통 패턴

다음 그룹을 각각 분석하고 비교한다.

- 직접 레퍼런스
- 인접 레퍼런스
- 주변 레퍼런스

기록 항목:

- 자주 반복되는 패턴
- 전체 공통 패턴보다 강한 요소
- 다른 그룹과 구별되는 요소
- YOVIA와의 관련성
- 대표 출처
- 예외·반대 사례

### 3. 디자인 적합도별 공통 패턴

다음 그룹을 각각 분석하고 비교한다.

- 핵심 디자인 레퍼런스
- 보조 디자인 레퍼런스
- 요소 참고 레퍼런스
- 비적합·반면교사

기록 항목:

- 선정 콘셉트와 일치하는 디자인 요소
- 일치 강도와 근거
- 제품 관련성 분류와의 교차 관계
- YOVIA가 직접 참고할 구조
- 일부만 차용할 요소
- 적용하면 안 되는 위험 요소

제품 관련성이 `주변`이어도 디자인 핵심군일 수 있으며, 제품 관련성이 `직접`이어도 디자인 비적합군일 수 있다. 두 축을 혼동하지 않는다.

### 4. 선정 디자인 콘셉트 검증

다음 항목을 검토한다.

- 선정 방식이 사용자 선택인지 근거 기반 추천인지
- 선정 콘셉트가 실제 공통 패턴과 대표 출처에 의해 지지되는지
- YOVIA의 파우치·내장 스푼·토핑을 설명하기 적합한지
- 제품 이해도와 디자인 차별성을 함께 확보하는지
- 모바일 1열 흐름으로 확장 가능한지
- 맛과 제품군이 늘어도 유지 가능한지
- 구현 난이도와 필요한 자산
- 실패 가능성과 중단 조건
- 대안으로 유지할 후보 콘셉트

사용자 선택 콘셉트는 존중하되, 원본 근거와 충돌하거나 구현 위험이 큰 경우 조건과 위험을 명시한다.

### 5. 세부 카테고리별 특화 패턴

분류 결과에 실제 존재하는 세부 카테고리와 보조 태그만 사용한다.

예:

- 요거트·스키르
- 파우치 제품
- 마시는 식사
- 휴대형 아침
- 기능성 식품
- 단백질 음료·바
- DTC 식품
- 제품 구조·사용법 중심 소비재
- 패키지·컬러 참고군
- 상품 탐색·커머스 참고군

### 6. 예외·차별화 사례

빈도는 낮지만 YOVIA에 중요한 사례를 별도로 기록한다.

- 제품 구조를 독특하게 설명한 사례
- 파우치·스푼·토핑과 유사한 복합 사용 경험
- 모바일에서 특히 효율적인 사례
- 높은 구현 난이도에도 차별성이 큰 사례
- 선정 콘셉트와 반대지만 일부 요소가 유효한 사례
- 선정 콘셉트의 약점을 보완할 대안 사례
- 참고하면 안 되는 반면교사

예외 사례는 전체 공통 패턴처럼 표현하지 않는다.

## 공통 패턴 판정 규칙

### 개별 사례

한 레코드에서만 확인된 요소다. 공통 패턴으로 확정하지 않는다.

### 반복 신호

서로 다른 2개 이상의 레코드에서 유사하게 관찰된 요소다. 추가 검토 대상으로 기록한다.

### 카테고리 특화 패턴

특정 분류 또는 세부 카테고리에서 반복되지만 전체 레퍼런스에서는 일반적이지 않은 요소다.

### 전체 공통 패턴

서로 다른 브랜드와 복수 분류에서 반복되고, 동일한 사용자 목적이나 정보 기능을 수행하는 요소다.

### 구조적 핵심 패턴

전체 또는 핵심 분류에서 반복되며 YOVIA의 정보 전달·탐색·구매 전환에 직접 영향을 주는 패턴이다.

단순히 표현이 비슷하다는 이유만으로 하나의 패턴으로 묶지 않는다. 다음 중 하나 이상이 같아야 한다.

- 해결하는 사용자 질문
- 정보의 우선순위
- 화면 내 위치와 흐름
- 상호작용 목적
- 전환 목표
- 제품 이해 방식

## 빈도 계산

분류 MD에 검증 가능한 집계값이 있으면 이를 우선 재사용한다. 분류 집계가 없거나 `분류 재검토 필요`로 판정된 항목만 원본 리서치에서 다시 계산한다.

가능한 경우 패턴별로 다음을 기록한다.

```text
관찰 레코드 수
유효 분석 대상 대비 비율
주로 나타난 분류
대표 출처 ID
예외 출처 ID
```

비율은 다음 방식으로 계산한다.

```text
패턴 관찰 레코드 수 ÷ 해당 패턴 필드가 확인된 분석 집단의 유효 레코드 수 × 100
```

규칙:

- 확인되지 않은 필드는 분모에서 제외할 수 있으며, 그 경우 실제 분모를 명시한다.
- 하나의 레코드는 동일 패턴 빈도에서 한 번만 센다.
- `partial` 레코드는 해당 필드가 확인된 경우에만 센다.
- 중복 공식 도메인은 대표 레코드만 센다.
- 숫자를 정확히 집계할 수 없으면 임의 추정하지 않는다.
- 정확한 집계가 불가능하면 `정확한 빈도 산출 불가`와 원인을 기록한다.

## 분석 절차

1. 리서치와 분류 결과의 버전·경로·레코드 수를 확인한다.
2. 제품 관련성과 디자인 적합도의 수량 공식을 검증한다.
3. 유효 분석 대상과 제외·보류 대상을 확정한다.
4. 분류 MD의 공통 디자인 집계값·콘셉트 후보·선정 콘셉트를 읽는다.
5. 원본 리서치에서 핵심 집계의 분자·분모·대표 출처를 대조한다.
6. 검증 통과한 집계값은 그대로 재사용한다.
7. 불일치 항목은 `분류 재검토 필요`로 기록하고 해당 수치에 기반한 확정 결론을 중단한다.
8. 전체 공통 패턴의 의미와 패턴 간 관계를 분석한다.
9. 직접·인접·주변 제품 관련성별 공통점과 차이를 분석한다.
10. 핵심·보조·요소 참고·비적합 디자인 적합도별 공통점과 차이를 분석한다.
11. 선정 디자인 콘셉트와 주·보조 콘셉트의 역할을 검증한다.
12. 제품 관련성과 디자인 적합도의 교차 사례를 분석한다.
13. 세부 카테고리별 특화 패턴을 분석한다.
14. 예외·차별화·반대 사례와 대안 콘셉트를 정리한다.
15. 패턴별 근거 강도와 YOVIA 관련성을 평가한다.
16. 관찰된 타사 패턴과 YOVIA 적용 제안을 분리한다.
17. 데스크톱과 모바일 적용 차이를 정리한다.
18. 적용 우선순위·구현 난이도·위험·중단 조건을 제시한다.
19. 결과를 저장하고 품질 검사를 수행한다.

## 원인과 해석의 한계

웹사이트에서 관찰된 요소끼리 함께 나타난다는 이유만으로 인과관계를 단정하지 않는다.

다음 표현을 구분한다.

- `관찰됨`: 원본 리서치에서 직접 확인
- `반복 확인됨`: 여러 레코드에서 반복
- `해석`: 관찰된 패턴을 바탕으로 한 제한적 판단
- `적용 제안`: YOVIA에 맞게 변환한 제안
- `추가 확인 필요`: 현재 자료로 확정할 수 없음

트래픽, 전환율, 매출, 사용자 선호 데이터가 없으면 특정 UX가 성과를 높였다고 단정하지 않는다.

## 패턴 평가 기준

각 핵심 패턴에는 다음 기준을 사용한다.

### 근거 강도

- `높음`: 여러 분류와 다수 레코드에서 반복되며 원본 근거가 명확함
- `중간`: 특정 분류에서 반복되거나 일부 레코드의 근거가 제한적임
- `낮음`: 소수 사례 또는 `partial` 레코드 중심이며 추가 확인이 필요함

### YOVIA 적합성

- `높음`: 파우치·내장 스푼·토핑의 결합 경험과 직접 연결됨
- `중간`: 제품 이해·탐색·신뢰·구매 전환을 보조함
- `낮음`: 시각 참고는 가능하지만 핵심 사용 경험과 연결이 약함

### 선정 콘셉트 타당성

- `높음`: 공통 디자인 집계, 복수 대표 출처, YOVIA 핵심 경험, 모바일 확장성이 모두 지지함
- `중간`: 방향은 적합하지만 일부 핵심 자산·제품 정보·구현 조건이 미확정임
- `낮음`: 사용자 취향 또는 소수 사례 중심이며 제품 이해·모바일·유지 가능성과 충돌함

### 구현 난이도

- `낮음`: 정적 레이아웃·카드·배지·일반 반응형으로 구현 가능
- `중간`: 필터·탭·아코디언·스티키 CTA·상태 전환 필요
- `높음`: 복합 모션·실시간 데이터·3D·고급 인터랙션·외부 시스템 연동 필요

### 적용 우선순위

- `필수`: 핵심 제품 이해와 전환에 직접 필요
- `우선`: 효과가 크고 현재 범위에서 실행 가능
- `선택`: 차별화에 도움이 되나 선행 조건이 필요
- `보류`: 근거·자원·제품 정보가 부족하거나 위험이 큼

점수만 제시하지 말고 각 판단 근거를 한 문장 이상 작성한다.

## YOVIA 분석 핵심 질문

모든 적용 제안은 최소한 다음 질문 중 하나에 답해야 한다.

1. 무엇이 들어 있는가?
2. 어떻게 열고 먹는가?
3. 언제 가장 편리한가?
4. 기존 제품보다 무엇이 덜 번거로운가?
5. 어떤 정보를 확인한 뒤 구매할 수 있는가?

질문과 연결되지 않는 장식적 제안은 우선순위를 낮춘다.

## 데스크톱과 모바일 구분

각 핵심 패턴은 데스크톱과 모바일 적용 차이를 함께 검토한다.

### 데스크톱

- 넓은 제품 비교
- 다열 제품 카드
- 제품 구조 인포그래픽
- 이미지와 설명의 병렬 배치
- 호버·탭·필터
- 깊은 탐색 경로

### 모바일

- 1열 세로 흐름
- 한 손 사용 가능한 CTA
- 단계별 사용법
- 카드형 비교
- 영양·원료·FAQ 아코디언
- 스크롤 고정 구매·판매처 CTA
- 터치 영역과 정보 축약

데스크톱 레이아웃을 단순 축소하여 모바일 권장안으로 제시하지 않는다.

## 관찰과 적용 제안 분리

각 핵심 패턴은 다음 구조로 작성한다.

```md
### 패턴명

#### 관찰된 공통점
- 실제 레퍼런스에서 반복된 구조
- 관찰 수와 비율
- 대표 출처
- 예외·반대 사례

#### 해석
- 해당 패턴이 해결하는 사용자 질문
- 분류별 차이
- 분석의 한계

#### YOVIA 적용 제안
- 적용 위치
- 필요한 콘텐츠
- 데스크톱 방식
- 모바일 방식
- 구현 난이도
- 위험과 중단 조건
- 적용 우선순위
```

타사 관찰과 YOVIA 제안을 한 문장에 섞지 않는다.

분석 결과가 없는 섹션을 억지로 채우지 않는다. 자료가 부족하면 `확인 가능한 근거 부족`이라고 쓴다.

## 출처 표기

1. 모든 핵심 패턴에 대표 출처 ID와 브랜드명을 함께 쓴다.

```text
[001] Chobani
[015] GoGo SqueeZ
```

2. 특정 관찰을 인용할 때는 원본 리서치의 섹션 또는 P1~P5 근거를 함께 적는다.
3. 최소 3개 이상의 서로 다른 레코드가 반복되어야 전체 공통 패턴으로 우선 제시한다.
4. 2개 레코드만 확인되면 반복 신호 또는 카테고리 특화 후보로 표시한다.
5. 하나의 레코드만 확인되면 예외·차별화 사례로 기록한다.
6. 우선 검토 브랜드만으로 200개 전체의 공통점이라고 결론 내리지 않는다.

## 피해야 할 오류

- `200개`라는 파일명만 보고 실제 레코드 수를 확인하지 않는 것
- 10~20개 대표 브랜드만 보고 전체 공통점이라고 쓰는 것
- 동일 도메인 중복을 빈도에 중복 계산하는 것
- `partial`의 미확인 필드를 관찰된 사실로 사용하는 것
- `dead`·`failed` 레코드를 정상 사례처럼 포함하는 것
- 분류 결과와 다른 그룹명을 임의로 만드는 것
- 분류의 공통 디자인 집계값을 검증 없이 버리고 전부 새로 계산하는 것
- 검증된 분류 집계값과 다른 수치를 이유 없이 제시하는 것
- 제품 관련성과 디자인 적합도를 같은 분류 축처럼 혼동하는 것
- 사용자 선택 콘셉트를 무시하거나, 반대로 위험 검토 없이 무조건 승인하는 것
- 선정 콘셉트를 최종 화면 설계가 확정된 것처럼 표현하는 것
- 분류 오류를 발견하고도 분류 파일을 분석 단계에서 직접 수정하는 것
- 제품 수치가 확정되지 않았는데 `0g`, `0%`처럼 구체화하는 것
- 타사의 기능과 YOVIA 적용안을 같은 사실처럼 쓰는 것
- 상관관계를 인과관계로 표현하는 것
- 트래픽·매출 데이터 없이 전환 효과를 확정하는 것
- 데스크톱의 넓은 표를 모바일에 축소 적용하는 것
- 모든 맛의 컬러를 동일 강도로 한 화면에 사용하는 것
- 목적이 없는 3D·파티클·복합 모션을 추천하는 것
- 분석 단계에서 원본 리서치나 분류 파일을 수정하는 것

## 품질 검사

저장 전 다음을 검사한다.

### 입력 무결성

- 리서치와 분류 파일이 모두 존재하는가?
- 두 파일의 레코드 ID와 버전이 연결되는가?
- 실제 레코드 수를 계산했는가?
- 제외·보류 기준이 명확한가?
- 제품 관련성과 디자인 적합도의 수량 공식이 성립하는가?
- 선정 콘셉트·선정 방식·주·보조 콘셉트 역할이 존재하는가?

### 분류 집계 검증

- 분류의 공통 디자인 집계값을 먼저 읽었는가?
- 핵심 집계의 분자·분모·출처를 원본과 대조했는가?
- 검증된 값은 재사용했는가?
- 불일치 값을 임의 수정하지 않고 `분류 재검토 필요`로 기록했는가?
- 중복·dead·failed·partial 처리 기준이 일치하는가?
- 핵심 패턴의 포함 ID 전체를 리서치 원문과 대조했는가?
- 포함 ID 수와 분자, 분자와 분모, 분모와 유효 대상의 수량 공식이 성립하는가?
- 대표 출처가 포함 ID에 있고 예외 출처가 제외·미확인 ID에 있는가?
- 분류와 분석의 패턴명·분자·분모·비율이 정확히 일치하는가?
- 불일치가 하나라도 남아 있는데 `분류 재검토 필요 항목: 없음`으로 표시하지 않았는가?

### 분석 정확성

- 전체 공통점이 실제 유효 대상에 기반하는가?
- 각 패턴에 관찰 수 또는 집계 불가 사유가 있는가?
- 대표 출처와 예외 출처가 연결되는가?
- 단일 사례를 전체 경향으로 과장하지 않았는가?
- 직접·인접·주변의 차이를 구분했는가?
- 핵심·보조·요소 참고·비적합의 차이를 구분했는가?
- 두 분류 축을 교차 분석했는가?
- `partial`과 미확인 정보를 확정 사실로 사용하지 않았는가?
- 제품 관련성·디자인 적합도 수량뿐 아니라 ID 집합도 분류 파일과 일치하는가?
- 분류 요약표와 상세 레코드가 충돌하면 이를 검증 완료로 처리하지 않았는가?

### 선정 콘셉트 타당성

- 선정 방식이 정확히 기록되었는가?
- 선정 콘셉트가 공통 패턴과 대표 출처에 의해 지지되는가?
- YOVIA 핵심 경험과 연결되는가?
- 모바일 확장성과 유지 가능성을 검토했는가?
- 구현 난이도와 필요한 자산을 기록했는가?
- 위험·중단 조건·대안 콘셉트를 포함했는가?

### 적용 타당성

- 관찰된 공통점과 YOVIA 적용 제안을 분리했는가?
- 데스크톱과 모바일을 구분했는가?
- 구현 난이도와 위험을 함께 기록했는가?
- 우선순위에 구체적인 이유가 있는가?
- 확정되지 않은 수치·기능을 만들지 않았는가?

### 문서 완성도

- 필수 구조를 따르는가?
- 모든 핵심 주장에 출처 ID가 있는가?
- 중복되거나 모순되는 결론이 없는가?
- 실제 분석 대상 수를 정확히 표기했는가?
- UTF-8 인코딩과 파일 끝 줄바꿈이 유지되는가?
- Phase 1은 `초기 분석·초기 결론`, Phase 2는 `중간 분석·중간 결론`, 최종 허용 단계만 `최종 분석·최종 결론`으로 표시했는가?
- Phase 1·2에서 1팀·2팀 최종 보고 실행 흔적이 없는가?

검사에 실패하면 완료로 보고하지 않는다. 수정 가능한 문제는 수정한 뒤 다시 검사하고, 외부 확인이 필요한 문제는 `추가 확인 필요` 또는 `분류 재검토 필요`로 남긴다.

# YOVIA 가상 클라이언트 생성·분석·설계 통합 자동화

## 1. 목적

이 파일은 YOVIA 브랜드·페르소나·리서치 근거에서 가상 클라이언트를 생성하고, 클라이언트별 사이트 분석 결과를 만든 뒤 설계 산출물을 생성·검증·분류하는 통합 자동화 실행 계약이다.

```text
브랜드·페르소나·리서치 근거
→ 가상 클라이언트 생성
→ 요구사항·출처 추적
→ 클라이언트별 리서치 사이트 분석
→ MENU / CONTENT / FUNCTION 분석 결과
→ 사이트맵
→ 서비스 흐름도
→ 화면 설계서·저충실도 와이어프레임·화면 목록
→ 전체 정합성 검증
→ 설계 출력물 유형별 분류
```

Figma와 스토리보드는 이 자동화 범위에 포함하지 않는다.

설계 프로젝트 루트:

```text
C:\kje\UIUXA\WIREFRAME
```

가상 클라이언트 생성 프로젝트:

```text
C:\kje\UIUXA\Md_Skill
```

생성 입력:

```text
Md_Skill\input\00_brand\
Md_Skill\input\02_virtual_client\
Md_Skill\input\03_persona\

Md_Skill\output\02_classification\YOVIA_REFERENCE_CLASSIFICATION.md [보조]
Md_Skill\output\03_analysis\YOVIA_RESEARCH_ANALYSIS.md [보조]
```

가상 클라이언트 생성 출력:

```text
Md_Skill\output\04_virtual_clients\YOVIA_VIRTUAL_CLIENT_MASTER.md
Md_Skill\output\04_virtual_clients\YOVIA_REQUIREMENT_MASTER.md
Md_Skill\output\04_virtual_clients\YOVIA_SOURCE_TRACEABILITY.md
Md_Skill\output\04_virtual_clients\clients\VC_{3자리 ID}.md
```

사이트 분석 입력:

```text

WIREFRAME\input\templates\가상클라이언트 기반 분석 결과 작성 양식.md
```

사이트 분석 출력:

```text
가상 클라이언트 분석 결과\VC_{3자리 ID}_{이름}.md
```

중간 통합 출력:

```text
가상 클라이언트 설계 결과\{3자리 ID}_{이름}\
```

최종 분류 출력:

```text

```

설계 지침 원본:

```text
설계 프롬프트\설계프롬프트.txt
```

## 3. 실행 요청 해석

다음 요청은 기존 분석 결과를 사용하는 단일 클라이언트 설계로 해석한다.

```text
11번 설계해
VC-011 설계해
VC_011_조은채 설계해
011_조은채 설계 결과 만들어줘
```

실행 대상은 분석 결과 폴더에서 ID로 찾는다.

```text
11 → 011 → VC_011_*.md
```

동일 ID 파일이 0개이면 중단한다. 동일 ID 파일이 2개 이상이면 자동 선택하지 않고 중단한다.

`전체 설계해` 요청은 정상 형식의 분석 파일을 ID 순서로 처리한다. 한 클라이언트의 결과를 다음 클라이언트에 복사하거나 평균화하지 않는다.

다음 요청은 가상 클라이언트 생성부터 설계까지 전체 실행으로 해석한다.

```text
가상 클라이언트 21번 생성하고 분석·설계해
VC-021 생성부터 설계까지 해
가상 클라이언트 21~30번 만들고 설계 결과까지 생성해
전체 파이프라인 실행해
```

사용자가 ID 범위 또는 수량을 지정하지 않으면 임의로 새 Client를 추가하지 않는다. 기존 정상 Client ID 다음 번호는 참고할 수 있지만 실제 생성 범위는 사용자의 명시적 요청으로 확정한다.

## 4. PHASE A — 가상 클라이언트 생성

### 실행 지침

다음 파일을 모두 읽는다.

```text
Md_Skill\AGENTS.md
Md_Skill\.agents\skills\virtual_client\SKILL.md
Md_Skill\input\00_brand\
Md_Skill\input\02_virtual_client\
Md_Skill\input\03_persona\
```

사용 가능한 경우 검증된 리서치·분류·분석 결과를 보조 근거로 읽는다. 검증되지 않은 음성은 추측하지 않고 `pending_transcription`으로 둔다.

### 생성 원칙

- 가상 클라이언트는 소비자 페르소나가 아니라 UX/UI 프로젝트의 합성 발주·검토 책임자다.
- 기존 Client와 사업 목표·판단 기준·정보 우선순위·UX 요구가 실질적으로 달라야 한다.
- 표현만 다른 중복 관점을 새 Client로 만들지 않는다.
- 이름·직책은 synthetic임을 유지한다.
- 모든 핵심 요구는 Source ID와 Evidence ID에 연결한다.
- YOVIA의 그릭요거트 기반 간편 건강식 정의를 변경하지 않는다.
- 가격·영양 수치·효능·판매 채널·인증·제품 사양을 임의 확정하지 않는다.

### Client별 필수 결과

```text
Md_Skill\output\04_virtual_clients\clients\VC_XXX.md
```

각 파일은 생성 정보, 역할, 담당 영역, 타깃, 사업·전환 목표, 사용자 문제, 정보·기능·UX·UI·콘텐츠·비주얼·신뢰·반응형 요구, 전체 Requirement, Client 관계, 추가 검증 필요를 포함한다.

### Requirement 계약

각 요구사항에는 다음을 기록한다.

```text
Requirement ID
Virtual Client ID
Request
Category
Priority
Source IDs
Evidence IDs
Evidence Confidence
Brand Fit 및 이유
Relationship Type
Conflict
Validation Needed
Notes
```

### 마스터 갱신

새 Client 생성 후 다음 세 파일을 전체 Client 기준으로 다시 집계한다.

```text
YOVIA_VIRTUAL_CLIENT_MASTER.md
YOVIA_REQUIREMENT_MASTER.md
YOVIA_SOURCE_TRACEABILITY.md
```

총 Client 수, Requirement 수, Must·Should·Could·Hold, 관계 유형, Brand Fit, Validation Needed의 합계가 실제 행 수와 일치해야 한다.

## 5. PHASE A 검증

- 요청한 Client ID와 이름이 고유한가?
- 기존 Client와 설계 의사결정 축이 중복되지 않는가?
- Client별 Requirement가 하나 이상 존재하는가?
- 모든 Requirement ID가 고유한가?
- 모든 Requirement가 Source/Evidence에 연결되는가?
- 브랜드 충돌·보류·미검증 요구가 삭제되지 않았는가?
- 세 마스터의 전체 집계가 실제 Client 파일과 일치하는가?
- 후속 분석 Skill이 읽을 수 있는 파일명 `VC_XXX.md`인가?

검증 실패 시 사이트 분석과 설계를 실행하지 않는다.

## 6. PHASE B — 가상 클라이언트 사이트 분석

### 실행 지침

다음 파일을 읽는다.

```text
WIREFRAME\AGENTS.md
WIREFRAME\.agents\skills\analyze\SKILL.md
WIREFRAME\input\templates\가상클라이언트 기반 분석 결과 작성 양식.md
Md_Skill\output\04_virtual_clients\clients\VC_XXX.md
Antigravity\research\batches\batch-*.txt
```

### 분석 공식

```text
가상 클라이언트 요구·목표·제약
+ 검증 가능한 리서치 사이트 관찰
+ YOVIA 브랜드 적합성
→ MENU / CONTENT / FUNCTION 후보
```

리서치 사이트에 존재한다는 이유만으로 요소를 자동 채택하지 않는다. 현재 Client의 Requirement와 연결되지 않는 요소는 제외한다.

### 유효 리서치 처리

- `dead`, `failed`, `discarded`, 샘플, 임시 자료는 정상 근거에서 제외한다.
- completed와 partial을 구분한다.
- 중복 도메인을 같은 사이트로 식별한다.
- 실제 유효 사이트 수를 기록한다.
- 저장된 자료만 검토한 경우 실제 클릭·구매·사용했다고 표현하지 않는다.

### 분석 출력

```text
WIREFRAME\가상 클라이언트 분석 결과\VC_XXX_{이름}.md
```

최상위 구조는 다음 6개를 같은 순서로 사용한다.

```text
1. 가상 클라이언트
2. 클라이언트 요구사항
3. 정보 구조
4. 내비게이션
5. 화면 구성
6. 검토 결과
```

MENU는 정보 구조·내비게이션에, CONTENT는 정보 구조·화면 구성에, FUNCTION은 요구사항·정보 구조·내비게이션·화면 구성의 적합한 위치에 기록한다.

Requirement ID를 축약하지 않고 대표 Site ID, 관찰 근거, 우선순위, 검증 상태와 연결한다.

## 7. PHASE B 검증

- 파일명이 `VC_XXX_{이름}.md`인가?
- Client 원본의 모든 Requirement가 반영·보류·제외 판단에 연결되는가?
- 실제 리서치 배치 자료를 읽었는가?
- 유효 사이트 수와 제외 기준이 기록됐는가?
- MENU / CONTENT / FUNCTION이 모두 존재하는가?
- 핵심 후보에 Requirement ID와 Site ID가 있는가?
- 1~6 고정 최상위 구조를 따르는가?
- 근거 없는 수치·기능·정책을 생성하지 않았는가?
- 이 단계에서 사이트맵·흐름도·화면 설계를 만들지 않았는가?

검증을 통과한 분석 결과만 다음 설계 단계의 입력으로 사용한다.

## 8. PHASE C 입력 분석

각 클라이언트마다 분석 결과를 처음부터 끝까지 읽고 다음을 추출한다.

- Client ID와 이름
- 프로젝트 주제와 제작 목적
- 사용자 유형과 사용 상황
- Requirement ID 전체
- 중요도
- MENU 후보
- CONTENT 후보
- FUNCTION 후보
- 내비게이션 후보
- 화면 구성 후보
- 근거 Site ID
- 보류·충돌·근거 부족
- 추가 검증 필요 항목

입력에 없는 제품명, 가격, 영양 수치, 판매 채널, 인증, 효능, 정책을 임의 생성하지 않는다.

## 9. 클라이언트 독립성

설계의 기준은 현재 처리 중인 분석 파일 하나다.

금지:

- 다른 Client의 사이트맵 복사
- 화면 수를 기존 Client와 맞추기
- 공통 템플릿에 이름과 색만 변경
- 다른 Client의 메뉴·CTA·기능 자동 병합
- 근거 없는 로그인·검색·구매 기능 확정

기존 설계 결과는 문서 형식과 파일 규격만 참고한다. 정보 구조와 사용자 흐름은 현재 Client의 Requirement에서 새로 도출한다.

## 10. STEP 1 — 사이트맵 생성

생성 파일:

```text
가상 클라이언트 설계 결과\{ID}_{이름}\사이트맵.md
가상 클라이언트 설계 결과\{ID}_{이름}\사이트맵.mmd
가상 클라이언트 설계 결과\{ID}_{이름}\사이트맵.svg
```

`사이트맵.md` 필수 내용:

- 프로젝트 개요
- 설계 근거와 핵심 사용자 목표
- 전역 내비게이션 구조
- 계층형 사이트맵
- 페이지 깊이 1차·2차·3차
- 페이지별 목적·핵심 콘텐츠·주요 기능·연결 페이지 표
- 공통 영역
- 회원 상태별 영역
- 주요 사용자 여정
- 예외 페이지
- 가정·HOLD·제외 항목
- 링크·중복·도달 가능성 검토
- Mermaid flowchart

`사이트맵.mmd`는 MD에 사용한 Mermaid 코드만 포함한다.

SVG 생성:

```powershell
npx -y @mermaid-js/mermaid-cli -i "사이트맵.mmd" -o "사이트맵.svg" -b transparent
```

## 11. STEP 2 — 서비스 흐름도 생성

입력:

```text
현재 Client 분석 결과
현재 Client 사이트맵.md
현재 Client 사이트맵.mmd
```

생성 파일:

```text
서비스_흐름도.md
서비스_흐름도.mmd
서비스_흐름도.svg
```

필수 내용:

- 서비스 흐름 개요
- 사용자 유형과 시작 조건
- 시작점과 종료점
- 핵심 정상 흐름
- 탐색 → 선택 → 상세 확인 → 핵심 행동 → 결과 확인
- 로그인 여부 분기
- 입력값 오류
- 결과 없음
- 이전 단계 이동
- 이탈과 재진입
- 시스템·외부 연결 오류
- 단계별 행동·시스템 처리·화면·다음 조건 표
- 전체 Mermaid flowchart
- 연결성 검토

분석 근거가 없는 로그인은 `가정`으로 표시한다. 불필요한 로그인 화면을 정상 흐름에 강제하지 않는다.

모든 화면 이름은 사이트맵과 한 글자도 다르지 않게 유지한다.

SVG 생성:

```powershell
npx -y @mermaid-js/mermaid-cli -i "서비스_흐름도.mmd" -o "서비스_흐름도.svg" -b transparent
```

## 12. STEP 3 — 화면 설계 생성

입력:

```text
현재 Client 분석 결과
현재 Client 사이트맵.md
현재 Client 서비스_흐름도.md
```

생성 파일:

```text
화면_설계서.md
와이어프레임.html
화면_목록.json
```

### 화면 ID

```text
SCR-001
SCR-002
SCR-003
...
```

사이트맵과 흐름도에 등장하는 모든 화면에 하나의 고유 ID를 부여한다. 세 파일에서 동일한 ID와 화면명을 사용한다.

### 화면 설계서 필수 내용

- 프로젝트 및 설계 범위
- 화면 ID 규칙
- 전체 화면 목록
- 화면별 목적·진입 조건·종료 조건
- 공통 헤더·푸터·내비게이션
- 화면 구성 영역과 UI 요소
- 표시 데이터
- 사용자 행동과 인터랙션
- 이동 대상
- 기본·로딩·빈 상태·오류·완료 상태
- 유효성 검사와 오류 메시지
- PC·태블릿·모바일 반응형 기준
- 접근성 요구사항
- Requirement 추적
- 가정·HOLD·제외 항목

### 와이어프레임 HTML 계약

- 외부 라이브러리 없이 단독 실행
- HTML·CSS·JavaScript를 하나의 파일에 포함
- 모든 화면 ID와 화면명 표시
- 사이드바 또는 상단 목차 제공
- 버튼과 링크가 `nextScreens`에 맞는 화면으로 이동
- 모바일·태블릿·PC 반응형
- 본문 바로가기와 키보드 포커스
- 이미지 플레이스홀더에 대체 텍스트
- 상태를 색상 외 텍스트로 병기
- 오류마다 복구 행동 제공

### 화면 목록 JSON 계약

최상위는 화면 배열이며 각 항목은 다음 필드를 모두 가진다.

```json
{
  "id": "SCR-001",
  "name": "홈",
  "purpose": "...",
  "entryConditions": ["..."],
  "sections": ["..."],
  "actions": ["..."],
  "states": ["기본", "로딩", "빈 상태", "오류", "완료"],
  "nextScreens": ["SCR-002"]
}
```

## 13. STEP 4 — 검증

### 파일 검증

정확히 9개 파일이 존재해야 한다.

```text
사이트맵.md
사이트맵.mmd
사이트맵.svg
서비스_흐름도.md
서비스_흐름도.mmd
서비스_흐름도.svg
화면_설계서.md
와이어프레임.html
화면_목록.json
```

### 구조 검증

- Mermaid MMD 2개가 오류 없이 SVG로 렌더링되는가?
- SVG가 `<svg` 요소를 포함하는가?
- SVG 한글 레이블이 깨지지 않는가?
- JSON이 파싱되는가?
- JSON의 화면 ID와 이름이 모두 고유한가?
- 사이트맵의 모든 페이지가 화면 목록에 존재하는가?
- 서비스 흐름의 모든 화면이 화면 목록에 존재하는가?
- JSON의 모든 `nextScreens`가 실제 ID인가?
- HTML에 JSON과 같은 화면 수가 있는가?
- HTML 내부 `#SCR-XXX` 링크가 실제 대상 ID를 가리키는가?
- HTML에 `viewport`, 본문 바로가기, 반응형 CSS가 있는가?
- Headless 브라우저에서 HTML이 열리는가?

### 내용 검증

- 현재 Client의 모든 Requirement ID가 설계와 연결되는가?
- MENU / CONTENT / FUNCTION이 누락되지 않았는가?
- 정상·분기·예외·복구 흐름이 존재하는가?
- 로그인·가격·재고·배송·효능 등 미확정 조건을 사실로 만들지 않았는가?
- 링크가 끊긴 화면이나 도달 불가능한 화면이 없는가?
- 중복 목적의 화면을 이유 없이 분리하지 않았는가?

검증 실패 시 `설계 출력물`에 복사하지 않는다. 실패 원인을 수정하고 전체 검증을 다시 실행한다.

## 14. STEP 5 — 설계 출력물 분류

검증을 통과한 9개 파일을 다음처럼 복사한다. `가상 클라이언트 설계 결과`의 원본은 보존한다.

```text
설계 출력물\사이트 구조맵\{ID}_{이름}\
├─ 사이트맵.md
├─ 사이트맵.mmd
└─ 사이트맵.svg

설계 출력물\서비스 흐름도\{ID}_{이름}\
├─ 서비스_흐름도.md
├─ 서비스_흐름도.mmd
└─ 서비스_흐름도.svg

설계 출력물\화면 설계서\{ID}_{이름}\
├─ 화면_설계서.md
├─ 와이어프레임.html
└─ 화면_목록.json
```

같은 Client의 분류 출력이 이미 있으면 덮어쓰기 전에 다음 위치로 보존한다.

```text
archive\previous\design-output\{timestamp}\{분류}\{ID}_{이름}\
```

## 15. 선행 입력 변경 시 재실행

### 브랜드·페르소나·근거 변경

변경 근거의 영향 Client를 식별한다. 가상 클라이언트의 Requirement 또는 Source/Evidence가 달라지면 해당 Client를 PHASE A부터 다시 실행한다.

```text
브랜드·페르소나·근거 변경
→ 영향 Client 생성 문서·마스터 재생성
→ 해당 Client 사이트 분석 재생성
→ 해당 Client 설계 9개 재생성
→ 전체 검증
→ 설계 출력물 재분류
```

### 가상 클라이언트 원본 변경

```text
Md_Skill\output\04_virtual_clients\clients\VC_XXX.md 변경
→ 해당 분석 결과 재생성
→ 해당 설계 전체 재생성
```

### 분석 결과 변경

분석 결과가 변경되면 해당 Client만 다시 실행한다.

```text
VC_012_강태윤.md 변경
→ 012_강태윤 기존 설계 결과 보존
→ 사이트맵부터 전체 재생성
→ 서비스 흐름도 재생성
→ 화면 설계 전체 재생성
→ 검증
→ 설계 출력물 재분류
```

선행 문서가 변경되면 후속 문서를 부분 수정하지 않고 다시 생성해 오래된 연결 관계를 남기지 않는다.

## 16. 중단 조건

- 사용자가 신규 Client ID·범위·수량을 지정하지 않음
- 필수 브랜드 자료가 없거나 읽을 수 없음
- 가상 클라이언트 생성 Skill이 없거나 읽을 수 없음
- 동일 Client ID가 중복됨
- Requirement의 Source/Evidence 추적이 끊김
- 가상 클라이언트 마스터 집계가 실제 행 수와 다름
- 분석 Skill 또는 분석 결과 작성 양식이 없음
- 유효 리서치 사이트가 0개
- 분석 결과가 MENU / CONTENT / FUNCTION 또는 1~6 구조 검증에 실패
- 분석 파일이 없거나 중복됨
- Client ID·이름·Requirement를 읽을 수 없음
- `설계프롬프트.txt`가 없음
- 사이트맵 Mermaid 렌더링 실패
- 서비스 흐름도 Mermaid 렌더링 실패
- JSON 파싱 실패
- 화면 이름·ID 불일치
- HTML 내부 링크 누락
- 도달 불가능한 정상 화면 존재
- 근거 없는 확정 정보가 포함됨

# YOVIA 가상 클라이언트 기반 사이트 분석 Skill

## 1. 목적

이 Skill의 목적은 **가상 클라이언트 자체를 요약하는 것**이 아니다.

가상 클라이언트를 하나의 분석 렌즈로 사용하여 기존 리서치 사이트 자료를 검토하고,
해당 클라이언트가 실제 프로젝트 발주자라고 가정했을 때 어떤 메뉴, 콘텐츠, 기능을
필요로 하는지 도출한다.

핵심 흐름:

```text
가상 클라이언트
→ 요구·목표·우선순위 파악
→ 리서치 사이트 자료 경험·검토
→ 가상 클라이언트 관점으로 유효성 판정
→ 반복·특화·충돌 패턴 분석
→ MENU / CONTENT / FUNCTION 도출
→ 가상 클라이언트별 분석 결과 저장
```

이 Skill은 후속 IA, 사이트맵, 서비스 흐름도, 화면 설계서, 와이어프레임을 생성하지 않는다.

## 3. 입력

### 3.1 가상 클라이언트 — 필수

기본 위치:

```text
C:\kje\UIUXA\Md_Skill\output\04_virtual_clients\clients\
```

예:

```text
VC_001.md
VC_002.md
VC_003.md
...
```

가상 클라이언트 파일은 **분석 기준**이다.

가상 클라이언트에서 우선 읽는 항목:

- Client ID
- 역할
- 프로젝트 관점
- 핵심 타깃
- 주요 사용 상황
- 사업 목표
- 전환 목표
- 핵심 사용자 문제
- 중요하게 보는 가치
- 정보 우선순위
- 기능 요구
- UX 요구
- UI 요구
- 콘텐츠 요구
- 비주얼 요구
- 신뢰 요구
- 전환·구매 요구
- 반응형·디바이스 요구
- 금지·회피 사항
- Requirement ID
- Requirement Priority
- Evidence / Source 연결
- Brand Fit
- Validation Needed
- 추가 검증 필요 항목

가상 클라이언트에 없는 목표·기능·사업 조건을 임의 생성하지 않는다.

---

### 3.2 분석 결과 작성 양식 — 필수

기본 위치:

```text
input/templates/가상클라이언트 기반 분석 결과 작성 양식.md
```

이 문서는 **분석 결과의 최우선 출력 계약(Output Contract)** 으로 사용한다.

분석 결과 문서는 이 양식의 최종 작성 구조를 임의로 바꾸지 않는다.

고정 최상위 순서:

```text
1. 가상 클라이언트
2. 클라이언트 요구사항
3. 정보 구조
4. 내비게이션
5. 화면 구성
6. 검토 결과
```

반드시 위 6개 최상위 섹션을 같은 순서로 사용한다.

다음과 같은 별도 최상위 섹션으로 대체하지 않는다.

```text
0. 분석 정보
MENU 분석 결과
CONTENT 분석 결과
FUNCTION 분석 결과
추적성
종합 검토
```

MENU / CONTENT / FUNCTION 분석 결과는 **양식 안에 배치**한다.

```text
MENU
→ 3. 정보 구조의 '메뉴'
→ 필요 시 4. 내비게이션의 이동·탐색 후보와 연결

CONTENT
→ 3. 정보 구조의 '콘텐츠'
→ 5. 화면 구성의 핵심·보조 콘텐츠와 연결

FUNCTION
→ 2. 클라이언트 요구사항의 '필요한 기능'
→ 3. 정보 구조의 콘텐츠·기능 해석
→ 4. 내비게이션 또는 5. 화면 구성의 적절한 위치에 연결
```

리서치 근거는 양식 구조를 깨지 않고 다음 필드에 연결한다.

```text
Requirement ID
관련 자료
대표 Site ID
관찰 근거
검증 상태
```

Requirement ID는 가상 클라이언트 원본의 ID를 **축약하지 않고 그대로 유지**한다.

예:

```text
VC001-REQ-001  → 유지
REQ-001        → 임의 축약 금지
```

양식의 5~8단계(계층 구조, 레이블, 내비게이션, 와이어프레임)는
현재 분석 단계에서 **최종 설계 확정으로 실행하지 않는다**.

대신 최종 작성 양식의 `4. 내비게이션`, `5. 화면 구성`에는
가상 클라이언트 요구와 리서치 사이트 근거에서 도출된 **분석 후보**만 작성한다.

예:

```text
허용:
- 제품 정보로 이동하는 경로가 필요함
- 헤더에서 제품 탐색 진입 요소가 필요함
- 모바일에서 핵심 정보 접근을 짧게 유지할 필요가 있음

금지:
- 최종 GNB를 6개로 확정
- URL 구조 확정
- 실제 화면 배치 확정
- 와이어프레임 생성
```

작성 양식이 없거나 읽을 수 없으면 실행을 중단한다.

### 3.3 리서치 사이트 자료 — 필수

기본 위치:

```text
C:\kje\UIUXA\Antigravity\research\batches\
```

이 디렉터리의 검증 가능한 리서치 결과를 분석 대상으로 사용한다.

가능한 자료 예:

- 사이트별 조사 MD
- 배치별 조사 결과
- 공식 URL
- 페이지 구조 기록
- UX/UI 관찰
- 제품 설명 방식
- 콘텐츠 구조
- 메뉴·내비게이션 관찰
- 인터랙션 기록
- 반응형 기록
- 스크린샷 또는 이미지 근거
- 상태 필드
- 출처 ID

### 리서치 자료 사용 원칙

- 실제 존재하는 자료만 사용한다.
- `failed`, `dead`, `discarded`, 샘플, 예시 파일은 정상 분석 근거로 사용하지 않는다.
- 중복 공식 도메인은 동일 사이트로 식별한다.
- 현재 실제 사용 가능한 사이트 수를 계산하고 기록한다.
- 자료가 200개 미만이어도 임의로 200개라고 작성하지 않는다.
- 저장된 조사 내용만으로 확인할 수 없는 인터랙션은 경험했다고 주장하지 않는다.
- 실제 브라우저 검증을 수행하지 않았다면 `직접 클릭`, `직접 사용`, `실제 테스트` 같은 표현을 사용하지 않는다.
- 이 Skill에서 말하는 “사이트 경험”은 **가상 클라이언트 관점에서 검증된 리서치 자료를 통해 해당 사이트의 구조·콘텐츠·기능을 평가하는 분석 행위**를 의미한다.

## 5. 분석 단위

최소 분석 단위:

```text
가상 클라이언트 × 리서치 사이트
```

예:

```text
VC_001 × SITE_001
VC_001 × SITE_002
VC_001 × SITE_003
...
```

가상 클라이언트마다 동일한 리서치 사이트 집합을 다시 분석한다.

이유:

- 가상 클라이언트마다 목표가 다르다.
- 중요하게 보는 정보가 다르다.
- 요구하는 기능이 다르다.
- 동일한 사이트 요소라도 가치를 다르게 평가할 수 있다.
- 특정 요소가 한 클라이언트에게는 핵심이지만 다른 클라이언트에게는 불필요할 수 있다.

클라이언트 간 결과를 처음부터 평균내거나 하나로 합치지 않는다.

## 6. 분석 원칙

### 6.1 분석 기준은 항상 가상 클라이언트다

리서치 사이트에서 요소를 발견했다고 자동 채택하지 않는다.

판정 흐름:

```text
사이트에서 요소 발견
→ 해당 가상 클라이언트의 요구와 관련 있는가?
→ 사용자 문제 해결에 기여하는가?
→ YOVIA 프로젝트 범위와 맞는가?
→ 검증 가능한 근거가 있는가?
→ MENU / CONTENT / FUNCTION 후보 여부 판정
```

### 6.2 리서치 사이트가 YOVIA 요구를 결정하지 않는다

금지:

```text
리서치 사이트에 있음
→ YOVIA에도 반드시 필요
```

허용:

```text
가상 클라이언트 요구가 있음
+
리서치 사이트에서 유효한 해결 패턴이 반복 관찰됨
→ YOVIA 적용 후보로 제안
```

### 6.3 사실과 제안을 분리한다

다음 상태를 구분한다.

```text
OBSERVED
리서치 자료에서 실제 관찰된 요소

CLIENT_REQUIRED
가상 클라이언트가 직접 요구하거나 Must/Should로 지정한 요소

DERIVED
클라이언트 요구 + 사이트 관찰을 결합해 도출한 분석 결과

HYPOTHESIS
근거가 약하거나 추가 검증이 필요한 제안

EXCLUDED
가상 클라이언트 요구 또는 YOVIA 범위와 맞지 않아 제외

CONFLICT
가상 클라이언트 요구와 다른 근거가 충돌
```

### 6.4 확인되지 않은 정보 생성 금지

다음을 임의 생성하지 않는다.

- 통계
- 비율
- 사용자 수
- 전환율
- 판매량
- 가격
- 인증
- 건강 효능
- 제품 사양
- 기능 구현 가능 여부
- 사이트가 실제 제공하지 않는 기능
- 리서치에서 확인되지 않은 인터랙션

근거가 없으면:

```text
not_verified
추가 검증 필요
```

로 남긴다.

## 7. 실행 순서

### STEP 0 — 입력 검사

확인:

- 가상 클라이언트 파일이 존재하는가?
- Client ID가 존재하는가?
- Requirement가 존재하는가?
- 분석 결과 작성 양식이 존재하는가?
- 리서치 사이트 자료 디렉터리가 존재하는가?
- 정상적으로 읽을 수 있는 리서치 자료가 존재하는가?
- 출력 디렉터리에 쓸 수 있는가?

핵심 입력이 없으면 중단한다.

---

### STEP 1 — 가상 클라이언트 분석 렌즈 생성

가상 클라이언트 파일에서 다음을 추출한다.

```text
Client Goal
Business Goal
User Problem
Target
Usage Context
Information Priority
UX Priority
UI Priority
Content Priority
Trust Priority
Conversion Priority
Responsive Priority
Constraints
Must Requirements
Should Requirements
Could Requirements
Hold Requirements
Validation Needed
```

분석용 내부 구조:

```yaml
client_lens:
  client_id:
  role:
  project_goal:
  primary_user_problems: []
  priority_requirements: []
  information_priorities: []
  ux_priorities: []
  trust_priorities: []
  conversion_priorities: []
  constraints: []
  validation_needed: []
```

이 내부 구조 자체를 별도 로그 파일로 만들지 않는다.

---

### STEP 2 — 리서치 사이트 자료 인벤토리

리서치 디렉터리를 스캔하여 분석 가능한 사이트 목록을 만든다.

각 사이트에서 가능한 범위 내 다음을 확인한다.

```text
Site ID
브랜드명
공식 도메인
URL 상태
조사 상태
메뉴/내비게이션
핵심 페이지 구조
콘텐츠 표현
제품 설명 방식
CTA
기능
인터랙션
반응형
신뢰 정보
시각적 특징
관련 메모
```

중복·실패·폐기·확인 불가 자료는 구분한다.

---

### STEP 3 — 가상 클라이언트 관점 사이트 경험

각 유효 사이트에 대해 다음 질문을 적용한다.

#### A. 목표 적합성

- 이 사이트의 어떤 요소가 현재 Client Goal과 연결되는가?
- 어떤 요소가 핵심 사용자 문제를 해결하는가?
- 어떤 요소는 현재 클라이언트에게 의미가 없는가?

#### B. 메뉴

- 사용자가 원하는 정보를 찾기 위한 메뉴 구조가 있는가?
- 제품 탐색에 도움이 되는 메뉴가 있는가?
- 브랜드·제품·사용법·신뢰·구매와 관련한 탐색 구조가 있는가?
- 해당 메뉴가 현재 가상 클라이언트에게 필요한 이유는 무엇인가?

#### C. 콘텐츠

- 어떤 정보 표현이 현재 요구를 해결하는가?
- 제품 이해를 돕는 콘텐츠는 무엇인가?
- 사용 상황을 이해시키는 콘텐츠는 무엇인가?
- 신뢰 형성 콘텐츠는 무엇인가?
- 비교·선택을 돕는 콘텐츠는 무엇인가?
- 불필요하거나 과도한 콘텐츠는 무엇인가?

#### D. 기능

- 사용자의 다음 행동을 돕는 기능은 무엇인가?
- 탐색·비교·확인·전환을 돕는 기능은 무엇인가?
- 모바일에서 특히 유효한 기능은 무엇인가?
- 클라이언트 요구와 맞지 않는 기능은 무엇인가?
- 구현 필요성이 불명확한 기능은 무엇인가?

#### E. 위험 및 충돌

- 브랜드 사실과 충돌하는가?
- 근거 없이 효과를 과장하는가?
- 현재 YOVIA 범위를 벗어나는가?
- 복잡성이 편익보다 큰가?
- 모바일 사용성을 해칠 가능성이 있는가?

### STEP 4 — 사이트별 관찰 기록

사이트마다 최소 다음 구조로 내부 관찰을 남긴다.

```yaml
site_observation:
  site_id:
  site_name:
  client_id:
  relevant_requirements: []
  menu_observations: []
  content_observations: []
  function_observations: []
  excluded_observations: []
  conflict_observations: []
  confidence:
```

내부 관찰은 최종 문서 작성에 사용한다.

사용자 요청이 없는 한 사이트별 개별 분석 파일을 수백 개 생성하지 않는다.

### STEP 5 — 반복·특화·충돌 패턴 집계

모든 유효 사이트 검토 후 다음을 구분한다.

```text
반복 패턴
여러 사이트에서 반복 관찰되며 클라이언트 요구와 맞는 요소

특화 패턴
소수 사이트에서만 보이지만 특정 클라이언트 요구를 강하게 해결하는 요소

보조 패턴
핵심은 아니지만 사용 흐름을 개선하는 요소

충돌 패턴
가상 클라이언트 요구, YOVIA 브랜드, 다른 확인 근거와 충돌하는 요소

제외 패턴
관련성이 낮거나 근거가 약한 요소
```

가능하면 다음을 계산한다.

```text
관찰 사이트 수
확인 가능한 사이트 수
관찰 비율
대표 Site ID
예외 Site ID
```

정확한 분모를 확인할 수 없으면 비율을 만들지 않는다.

## 8. MENU / CONTENT / FUNCTION 도출 규칙

MENU / CONTENT / FUNCTION은 반드시 분석하지만,
최종 문서에서 별도 최상위 섹션으로 분리하지 않는다.

최종 출력 위치:

```text
MENU     → 3. 정보 구조 / 4. 내비게이션
CONTENT  → 3. 정보 구조 / 5. 화면 구성
FUNCTION → 2. 클라이언트 요구사항 / 3. 정보 구조 / 4~5의 적절한 필드
```

세 축의 근거는 Requirement ID와 Site ID로 연결한다.

---

### 8.1 MENU

MENU는 사이트 구조를 확정하는 단계가 아니라 **필요한 탐색 항목 후보**를 도출하는 단계다.

포함 가능한 항목:

- 브랜드
- 제품
- 제품군
- 사용법
- 성분·영양
- FAQ
- 구매
- 지원
- 기타 클라이언트 요구에서 근거가 있는 탐색 항목

금지:

- 전체 사이트맵 확정
- 최종 Depth 확정
- GNB 개수 임의 확정
- 페이지 URL 구조 확정

각 MENU 후보는 다음을 기록한다.

```text
항목명
필요 이유
연결 Requirement ID
대표 리서치 Site ID
관찰 수 / 확인 가능 분모
우선순위
판정 상태
```

---

### 8.2 CONTENT

CONTENT는 사용자가 이해·판단·선택하기 위해 필요한 정보 후보를 의미한다.

각 CONTENT 후보는 다음을 기록한다.

```text
콘텐츠명
사용자 질문
해결 목적
연결 Requirement ID
대표 리서치 Site ID
관찰 패턴
우선순위
근거 상태
```

콘텐츠 카피 자체를 최종 확정하지 않는다.

---

### 8.3 FUNCTION

FUNCTION은 탐색·이해·비교·확인·전환을 돕는 작동 요소 후보를 의미한다.

각 FUNCTION 후보는 다음을 기록한다.

```text
기능명
해결 문제
사용자 행동
연결 Requirement ID
대표 리서치 Site ID
관찰 패턴
우선순위
검증 필요 여부
구현 관련 주의
```

구현 기술을 확인하지 않은 상태에서 실제 개발 가능성을 확정하지 않는다.

---

## 9. 우선순위

가상 클라이언트의 Requirement Priority를 최우선으로 반영한다.

기본 변환:

```text
Must   → 높음
Should → 중간 이상
Could  → 낮음 또는 선택
Hold   → 보류
```

단, 리서치 근거가 전혀 없다고 Must 요구를 삭제하지 않는다.

이 경우:

```text
Priority: 높음
Research Support: not_verified
Additional Validation: true
```

로 남긴다.

반대로 사이트에서 반복적으로 관찰되었다는 이유만으로
클라이언트와 무관한 요소를 높은 우선순위로 올리지 않는다.

```md

|---|---|---|---|---|
| {원본 Requirement ID} | ... | 높음·보통·낮음·보류 | {Evidence / Site ID} | ... |

작성 규칙:
- 가상 클라이언트 원본 요구를 가능한 한 구체적인 항목으로 나눈다.

- Requirement ID는 원본 ID를 축약하지 않는다.

작성 규칙:
- 정보 유형은 `사실 / 개념 / 절차 / 과정` 중 하나 이상으로 표시한다.
- 주제 → 부주제 → 메뉴 → 콘텐츠 순서로 분해한다.
- MENU 결과는 `메뉴` 열에 배치한다.
- CONTENT 결과는 `콘텐츠` 열에 배치한다.
- FUNCTION 결과는 `기능/화면 요소` 열에 배치한다.
- 같은 목적의 항목은 통합하고, 중복·불필요 항목은 제외한다.
- 리서치 사이트에서 관찰됐다는 이유만으로 자동 채택하지 않는다.
- 최종 사이트맵, 최종 Depth, URL 구조는 확정하지 않는다.
```

## 11. 가상 클라이언트 반복 실행

사용자가 전체 가상 클라이언트 분석을 요청하면
가상 클라이언트 저장소의 정상 Client 파일을 순서대로 실행한다.

```text
VC_001
→ 사이트 경험 분석
→ VC_001_ANALYSIS.md 저장

VC_002
→ 사이트 경험 분석
→ VC_002_ANALYSIS.md 저장

VC_003
→ 사이트 경험 분석
→ VC_003_ANALYSIS.md 저장

...

마지막 VC까지 반복
```

각 Client는 독립적으로 분석한다.

금지:

- 이전 Client 결론을 다음 Client의 기준으로 사용
- 앞선 Client의 MENU / CONTENT / FUNCTION을 다음 Client에게 자동 복사
- 서로 다른 Client의 요구를 조기에 통합
- 결과 수를 맞추기 위한 임의 복제

같은 항목이 여러 Client에서 반복 도출되는 것은 허용하지만,
각 Client의 자체 근거를 독립적으로 확인해야 한다.

---

## 12. 기존 출력 처리

같은 Client ID의 기존 정상 분석 결과가 있을 경우,
새 분석 결과로 덮어쓰기 전에 기존 파일을 아카이브한다.

기본 위치:

```text
archive/previous/analysis/
```

파일명:

```text
YYYYMMDD_HHMMSS__VC_001_ANALYSIS.md
```

검증 실패 결과:

```text
archive/failed/analysis/
```

폐기 결과:

```text
archive/discarded/analysis/
```

원본 가상 클라이언트와 리서치 자료는 수정·이동·삭제하지 않는다.

---

## 13. 선행 입력 변경 시 처리

### 가상 클라이언트가 변경된 경우

해당 Client의 기존 분석 결과를 아카이브하고 다시 분석한다.

```text
VC_004.md 변경
→ 기존 VC_004_ANALYSIS.md 아카이브
→ VC_004만 재분석
```

다른 Client가 변경되지 않았다면 전체를 자동 재분석하지 않는다.

### 리서치 사이트 자료가 변경된 경우

새로운 사이트가 추가되거나 기존 사이트 근거가 변경되면
영향을 받는 Client 분석 결과를 재검증한다.

전체 재실행이 필요한지 여부는 다음으로 판단한다.

- 분석 대상 사이트 수 변화
- 기존 핵심 패턴 변화
- 핵심 근거 Site 변경
- 새 패턴 등장
- 기존 패턴 반박 자료 등장

## 14. 완료 검증

가상 클라이언트별로 다음을 모두 확인한다.

```text
[ ] 올바른 Client ID를 사용했는가

[ ] 리서치 사이트 자료를 실제로 읽었는가
[ ] 실제 유효 사이트 수를 기록했는가
[ ] 사이트에 있다는 이유만으로 요소를 채택하지 않았는가
[ ] MENU 결과가 존재하는가
[ ] CONTENT 결과가 존재하는가
[ ] FUNCTION 결과가 존재하는가
[ ] 각 핵심 결과에 Requirement ID가 연결되는가
[ ] 각 핵심 결과에 Site 근거가 연결되는가
[ ] 근거 없는 수치·기능을 생성하지 않았는가
[ ] 충돌·제외·보류 항목을 삭제하지 않았는가
[ ] 예시 MD의 내용을 복사하지 않았는가
[ ] 다른 Client 결과를 자동 복제하지 않았는가
[ ] 최종 결과의 최상위 섹션이 1~6 양식 순서를 그대로 따르는가
[ ] `0. 분석 정보`, `MENU 분석 결과`, `CONTENT 분석 결과`, `FUNCTION 분석 결과`, `추적성` 등을 별도 최상위 섹션으로 만들지 않았는가
[ ] MENU / CONTENT / FUNCTION을 양식 내부 필드에 배치했는가
[ ] Requirement ID를 원본 형식 그대로 유지했는가
[ ] 4. 내비게이션과 5. 화면 구성은 최종 확정이 아니라 분석 후보로 작성했는가
[ ] 사이트맵을 만들지 않았는가
[ ] 서비스 흐름도를 만들지 않았는가
[ ] 화면 설계서를 만들지 않았는가
[ ] 와이어프레임을 만들지 않았는가
```

핵심 항목이 하나라도 실패하면 `완료`로 판정하지 않는다.

특히 출력 양식이 1~6 고정 구조를 따르지 않으면
분석 내용이 타당하더라도 `출력 양식 검증 실패`로 판정하고 수정 후 다시 저장한다.

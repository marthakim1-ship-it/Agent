### 3.1 유사 항목 분류

- **같은 목적의 통합**: 동일한 메뉴에 연결된 Requirement는 하나의 정보 그룹으로 묶고, 각 Requirement ID와 근거는 유지했다.
- **중복 처리**: 같은 의미의 메뉴·콘텐츠·기능은 대표 레이블 아래 통합했다. 서로 다른 검증 상태나 적용 범위는 합치지 않았다.
- **제외·보류**: 보류, HOLD, NOT_VERIFIED 항목은 확정 메뉴·CTA·카피에서 제외하고 검토 상태로 남겼다.
- **노출 우선순위**: 높음 요구를 핵심 정보, 보통 이상을 보조 정보, 보류를 비공개 검증 항목으로 배치한다.
- **자료 유형**: 제품 형태·구조는 이미지, 사용 순서는 이미지·영상, 사실·주의·정책은 텍스트, 수치·상태·비교는 검증된 데이터셋으로 분류한다. 실제 자료가 없으면 대체 자산을 생성하지 않는다.

### 3.2 계층 구조

```text
체험·샘플링 프로그램
├─ 핵심 정보
│  ├─ 체험 안내
│  │  └─ 체험 목적·구성·대상·주의 · 신청 전 조건 요약
│  ├─ 구성 상태
│  │  └─ 확정 구성과 예시·콘셉트 구성 · 구성 상태 라벨

│  ├─ 제품 정보

│  │  └─ 현장 QR 진입 맥락과 복구 · 딥링크 맥락 안내
├─ 검증·운영
│  ├─ 피드백
│  │  └─ 피드백 목적·보관기간·선택 여부 · 선택 동의
│  ├─ 검증 상태
```

- **메뉴 후보 원본 수**: 6개
- **통합 상위 그룹 수**: 3개
- **메뉴 폭 검토**: 조건부 적합 — 상위 그룹 3개로 권장 폭보다 작지만 Client 과업에 없는 메뉴를 추가하지 않는다.
- **메뉴 깊이 검토**: 프로젝트 → 상위 그룹 → 메뉴 → 콘텐츠·기능의 3단계로, 최대 5단계 이내다.
- **레이블 검토**: 메뉴는 Requirement 목적을 드러내는 명사형으로 분리했고 같은 의미의 레이블을 중복 사용하지 않는다.

## 4. 내비게이션

- **시작 화면**: 메인페이지 또는 체험 안내 관련 직접 진입 후보
- **이동 경로**: 메인페이지 → 카테고리 → 상품 후보 → 체험 구성 확인 → 체험 신청 상태 → 결과 확인·이전 단계
- **연결 페이지**: 브랜드 소개, 카테고리, 체험 구성 확인, 체험 신청 상태
- **검색 및 위치 안내**: 현재 위치와 상태를 텍스트로 표시하며 최종 GNB·URL은 확정하지 않음

### 4.1 내비게이션 유형 검토

- **글로벌 내비게이션 후보**: 핵심 정보, 상태·행동, 검증·운영. 이는 Client별 상위 탐색 그룹이며 최종 GNB 확정안이 아니다.
- **로컬 내비게이션 후보**: 각 상위 그룹 아래에 위 계층 구조의 메뉴 후보를 배치한다.
- **브레드크럼**: 직접 진입과 현재 위치 이해가 필요한 화면에서 상위 그룹 → 메뉴 → 현재 콘텐츠 경로 후보를 제공한다.
- **검색창**: 실제 문서량·검색어·색인 정책이 확인된 경우에만 적용하며, 미확정이면 `not_verified`로 유지한다.
- **풀다운 메뉴**: 하위 메뉴가 복수이고 모바일 접근성·키보드 동작이 검증된 경우에만 사용한다.
- **사이트맵**: 위 계층 구조를 후보로 사용하되 다른 Client 결과와 통합하기 전에는 최종 사이트맵으로 확정하지 않는다.
- **레이블 일관성**: 글로벌·로컬·브레드크럼·링크에서 동일한 메뉴명을 유지한다.
## 5. 화면 구성

- **헤더**: 브랜드·제품 정보에서 체험 안내로 진입하는 후보를 검토하되 체험 모집을 확정 상태로 표시하지 않는다.
- **내비게이션**: 대상·구성·조건·일정·신청 상태와 복귀 경로를 순서대로 안내한다.
- **핵심 콘텐츠**: YOVIA 정의, 체험·샘플링 프로그램 핵심 조건, 근거·기준일·상태
- **보조 콘텐츠**: 체험 구성 상태, 제품·주의 정보, QR 복귀 경로와 선택 피드백 조건.
- **푸터**: 개인정보·배송·참여 정책은 프로그램과 운영 책임이 확정된 경우에만 연결한다.

## 6. 검토 결과

- **누락 항목**: 체험 대상·구성·수량·일정·배송·선정·개인정보 처리와 신청 채널이 필요하다.
- **중복 항목**: 제품 소개와 체험 참여 조건을 구분하고 신청 전 판단 정보를 한 흐름으로 묶었다.
- **사용자 관점의 개선점**: 신청 전에 대상 여부, 제공 내용, 부담과 개인정보 사용 범위를 확인할 수 있어야 한다.
- **수정 사항**: MENU는 체험 안내, CONTENT는 구성·조건·상태, FUNCTION은 구성 카드·조건 체크리스트 후보로 정리했다.
- **보류·충돌·근거 부족**: 실제 체험 운영과 신청·선정·배송 정책은 `NOT_VERIFIED/HOLD`다.
- **검증 결론**: 조건부 완료. 프로그램 확정 전 신청 기능이나 제공 혜택을 생성하지 않는다.
### 6.1 반복 검토 체크리스트

- **요청 반영**: 원본 Requirement ID가 요구사항 표와 정보 구조에 모두 연결되어 있다.
- **누락·중복**: 누락 입력은 별도로 기록하고 중복 후보는 대표 레이블로 통합했다.
- **탐색 가능성**: 시작 화면, 이동 경로, 연결 페이지와 현재 위치 안내를 명시했다.
- **메뉴 깊이**: 3단계로 최대 5단계 이내다.
- **항목명 일관성**: 계층 구조·내비게이션·화면 구성에서 같은 명칭을 사용한다.
- **구조 변경 영향**: 상위 그룹 변경 시 로컬 메뉴·브레드크럼·관련 링크·화면 제목을 함께 점검한다.
- **웹·모바일 일관성**: 의미·우선순위·행동 순서를 유지하고 배치만 반응형으로 조정한다.

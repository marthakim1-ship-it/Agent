# 가상클라이언트 기반 분석 결과 — VC-021 (김서준)

## 1. 가상 클라이언트

- **프로젝트 주제**: 외부 검색이나 공유 링크로 YOVIA의 개별 페이지에 직접 들어온 사용자가 검색 질문에 맞는 답과 검증된 제품 정보를 빠르게 찾도록 정보의 발견성을 높인다.
- **제작 목적**: 페이지마다 고유한 질문과 답을 제공하고 제품·사용법·원료·검증 정보를 맥락 있게 연결한다. 실제 승인 자료가 없는 가격·재고·리뷰·효능은 검색 노출 정보로 만들지 않는다.
- **제공 자료**: `SRC-BRAND-001`, `SRC-REF-001`, `SRC-REF-002`, `SRC-REF-003`, `EVD-0034`; 리서치 `SITE-001~SITE-200` 중 유효 197개.
- **적용 매체**: 모바일 웹 우선, 데스크톱 확장. 검색 결과·공유 링크·상세 URL 직접 진입에서도 브랜드, 현재 페이지의 목적, 관련 정보로의 이동 맥락을 유지한다.

MENU 후보는 `페이지 안내`, `현재 위치`, `관련 정보`, `모바일 안내`, `검증 정보`의 5개다. 이는 정보 접근을 돕는 탐색 항목 후보이며 최종 GNB·사이트맵·URL 구조가 아니다. `페이지 안내`와 `모바일 안내`는 독립 메뉴보다 페이지 맥락 요소로 통합할 수 있다.

CONTENT 후보는 사용자 질문, 한 문장 답변, 페이지별 고유 제목·요약, 브랜드·제품 맥락, 제품·사용법·원료·검증 근거, 관련 링크 설명, 출처·기준일·적용 범위, 확인·준비 중·미확정 상태의 8개다. 가격·재고·리뷰·효능은 승인 자료 확보 전 공개 콘텐츠에서 제외한다.

FUNCTION 후보는 제목 계층, 현재 위치 표시, 맥락형 내부 링크, 관련 콘텐츠 카드, 모바일 직접 진입 안내, 검증 상태 라벨, 근거 문서 연결, 미확정 정보 공개 통제의 8개다. 검색창, 자동완성, 구조화 데이터 유형과 색인 정책은 직접 요구와 운영 기준이 부족해 `not_verified`다.

### 3.1 유사 항목 분류

- **같은 목적의 통합**: 동일한 메뉴에 연결된 Requirement는 하나의 정보 그룹으로 묶고, 각 Requirement ID와 근거는 유지했다.
- **중복 처리**: 같은 의미의 메뉴·콘텐츠·기능은 대표 레이블 아래 통합했다. 서로 다른 검증 상태나 적용 범위는 합치지 않았다.
- **제외·보류**: 보류, HOLD, NOT_VERIFIED 항목은 확정 메뉴·CTA·카피에서 제외하고 검토 상태로 남겼다.
- **노출 우선순위**: 높음 요구를 핵심 정보, 보통 이상을 보조 정보, 보류를 비공개 검증 항목으로 배치한다.
- **자료 유형**: 제품 형태·구조는 이미지, 사용 순서는 이미지·영상, 사실·주의·정책은 텍스트, 수치·상태·비교는 검증된 데이터셋으로 분류한다. 실제 자료가 없으면 대체 자산을 생성하지 않는다.

### 3.2 계층 구조

```text
외부 검색이나 공유 링크로 YOVIA의 개별 페이지에 직접 들어온 사용자가 검색 질문에 맞는 답과 검증된 제품 정보를 빠르게 찾도록 정보의 발견성을 높인다.
├─ 이용 안내
│  ├─ 모바일 안내
│  │  └─ YOVIA 정의와 현재 페이지 범위 · 축약 맥락 안내·상위 이동
│  ├─ 페이지 안내
│  │  └─ 자연어 질문과 검증 범위 내 한 문장 답변 · 질문·답 도입부
│  ├─ 현재 위치
│  │  └─ 페이지별 고유 제목과 탐색 목적 · 제목 계층·위치 안내
├─ 행동·지원
│  ├─ 관련 정보
│  │  └─ 이동 후 확인할 내용을 설명하는 링크 · 맥락형 내부 링크·관련 콘텐츠 카드
├─ 신뢰·안전 정보
│  ├─ 검증 정보
│  │  └─ 출처·기준일·적용 범위와 확인 상태 · 상태 라벨·근거 연결
```

- **메뉴 후보 원본 수**: 5개
- **통합 상위 그룹 수**: 3개
- **메뉴 폭 검토**: 조건부 적합 — 상위 그룹 3개로 권장 폭 5~9개보다 작지만 현재 Client의 제한된 과업 범위에 불필요한 메뉴를 추가하지 않는다.
- **메뉴 깊이 검토**: 프로젝트 → 상위 그룹 → 메뉴 → 콘텐츠·기능의 3단계로, 최대 5단계 이내다.
- **레이블 검토**: 상위 그룹과 메뉴는 명사형으로 통일하고, 같은 의미의 레이블은 하나로 합쳤다. 이름만 보고 목적을 알 수 없는 상태·기술 분류명은 사용자용 메뉴로 사용하지 않는다.
## 4. 내비게이션

- **시작 화면**: 홈이 아닌 상세 페이지에 직접 진입해도 페이지 상단에서 YOVIA, 현재 질문, 검증된 한 문장 답과 정보 범위를 이해할 수 있어야 한다 (`VC021-REQ-001`, `VC021-REQ-004`; `SITE-001`, `SITE-002`, `SITE-006`, `SITE-077`).
- **이동 경로**: 사용자 질문 → 한 문장 답변 → 제품·사용법·원료·검증 근거 → 관련 정보 → 확정된 다음 행동의 후보 순서를 유지한다 (`VC021-REQ-001~005`).
- **연결 페이지**: 제품 정보는 사용법·원료·검증 정보로 연결하고, 각 링크에는 이동 후 확인할 내용을 명시한다. 미확정 가격·재고·리뷰·효능은 관련 링크나 구매 CTA에 연결하지 않는다 (`VC021-REQ-003`, `VC021-REQ-005~006`).
- **검색 및 위치 안내**: 현재 위치와 상위·관련 정보 이동은 직접 진입 맥락을 복구하는 후보로 둔다. 실제 검색어 수요, 사이트 검색, URL·메타데이터·색인 정책은 추가 검증이 필요하다.

### 4.1 내비게이션 유형 검토

- **글로벌 내비게이션 후보**: 이용 안내, 행동·지원, 신뢰·안전 정보. 이는 Client별 상위 탐색 그룹이며 최종 GNB 확정안이 아니다.
- **로컬 내비게이션 후보**: 각 상위 그룹 아래에 위 계층 구조의 메뉴 후보를 배치한다.
- **브레드크럼**: 직접 진입과 현재 위치 이해가 필요한 화면에서 상위 그룹 → 메뉴 → 현재 콘텐츠 경로 후보를 제공한다.
- **검색창**: 실제 문서량·검색어·색인 정책이 확인된 경우에만 적용하며, 미확정이면 `not_verified`로 유지한다.
- **풀다운 메뉴**: 하위 메뉴가 복수이고 모바일 접근성·키보드 동작이 검증된 경우에만 사용한다.
- **사이트맵**: 위 계층 구조를 후보로 사용하되 다른 Client 결과와 통합하기 전에는 최종 사이트맵으로 확정하지 않는다.
- **레이블 일관성**: 글로벌·로컬·브레드크럼·링크에서 동일한 메뉴명을 유지한다.
## 5. 화면 구성

- **헤더**: 모바일 직접 진입에서도 브랜드명과 현재 페이지의 목적을 식별하고 상위 정보로 이동할 수 있는 후보를 검토한다. 최종 메뉴 구성과 개수는 확정하지 않는다 (`VC021-REQ-002`, `VC021-REQ-004`).
- **내비게이션**: 현재 위치, 상위 정보, 현재 질문과 가까운 관련 정보를 텍스트로 명확히 표시한다. 링크 이름은 이동 결과를 예측할 수 있게 작성한다 (`VC021-REQ-002~003`).
- **핵심 콘텐츠**: 페이지별 고유 질문과 한 문장 답변을 먼저 제시하고, 실제 제품·사용법·원료·문서 근거를 그 아래에서 확인하도록 한다 (`VC021-REQ-001`, `VC021-REQ-005`).
- **보조 콘텐츠**: 관련 정보 카드에는 링크명, 짧은 설명, 검증 상태를 함께 제공하는 후보를 둔다. 검색 의도와 무관한 장식이나 반복 카피가 핵심 답보다 앞서지 않게 한다 (`VC021-REQ-003`).
- **푸터**: 정책·판매 채널·책임 정보 연결은 실제 운영 자료가 확정된 경우에만 검토한다. 현재 푸터 구성과 구매 CTA는 `not_verified`다.

### 5.1 화면 배치 우선순위

| 화면 영역 | 배치 원칙 | 자료 유형 |
|---|---|---|
| 헤더 | 브랜드 식별과 현재 Client의 핵심 상위 탐색을 우선하고 미확정 CTA는 제외 | 텍스트·로고 |
| 내비게이션 | 현재 위치, 상위·하위 메뉴, 이전 단계와 관련 정보 연결 | 텍스트·링크 |
| 바디 | 높음 Requirement의 핵심 사실·과정·이미지를 먼저 배치 | 텍스트·이미지·영상·검증 데이터 |
| 어사이드 | 관련 자료, 기준일, 상태, 보조 행동만 배치하며 모바일에서는 본문 뒤로 이동 | 텍스트·상태 데이터 |
| 푸터 | 확정된 기업·정책·문의·저작권 정보만 연결 | 텍스트·링크 |

- **사용자 행동 경로**: 핵심 정보 이해 → 조건·근거 확인 → 관련 정보 비교 → 확정된 다음 행동 순서를 유지한다.
- **반응형 원칙**: 웹과 모바일에서 정보 의미와 이동 순서는 동일하게 유지한다. 모바일에서는 1열로 재배치하되 핵심 정보·주의·CTA의 상대적 우선순위를 바꾸지 않는다.
- **화면 전환 원칙**: 링크명과 도착 화면의 제목을 일치시키고 오류·빈 상태·보류 상태에서는 이전 유효 화면과 상시 정보로 복귀할 수 있게 한다.
## 6. 검토 결과

- **누락 항목**: 원본 6개 Requirement를 요구사항·정보 구조·내비게이션·화면 구성의 후보 또는 보류 판단에 모두 연결했다. 실제 검색 수요와 검색어, URL·제목·설명 정책, 구조화 데이터 유형, 색인 정책, 제품·가격·재고·리뷰 데이터는 추가 입력이 필요하다.
- **중복 항목**: 페이지 고유성, 직접 진입 맥락, 내부 연결을 구분하면서 질문→답→근거→관련 정보라는 하나의 사용자 흐름으로 정리했다. 다른 가상 클라이언트의 요구는 VC-021의 근거로 사용하지 않았다.
- **사용자 관점의 개선점**: 검색 사용자는 홈부터 탐색하지 않으므로 어느 상세 URL에서 시작하더라도 현재 페이지가 어떤 질문에 답하는지, 답의 근거가 무엇인지, 다음에 무엇을 확인할 수 있는지를 첫 화면에서 판단할 수 있어야 한다.
- **수정 사항**: 기존의 자동 분석식 `분석 개요`, `레퍼런스 분석`, `MENU/CONTENT/FUNCTION`, `최종 설계 방향` 구조를 지정 양식의 1~6번 구조로 재배치했다. 근거 없는 필수 화면군, 로그인, 알림 신청과 입력 오류 화면 가정을 제거했다.
- **보류·충돌·근거 부족**: 실제 검색량과 검색어, 사이트 검색, URL·메타데이터, 구조화 데이터, 색인 정책은 `not_verified`다. 미확정 가격·재고·리뷰·효능은 `HOLD`로 유지하며 검색 노출 정보나 CTA로 생성하지 않는다.
- **검증 결론**: 조건부 완료. MENU 5개, CONTENT 8개, FUNCTION 8개 후보를 지정 양식에 맞게 정리했으며 확정되지 않은 검색·상업 데이터는 후보로 확정하지 않았다.
### 6.1 반복 검토 체크리스트

- **요청 반영**: 원본 Requirement ID가 요구사항 표와 정보 구조에 모두 연결되어 있다.
- **누락·중복**: 누락 입력은 별도로 기록하고 중복 후보는 대표 레이블로 통합했다.
- **탐색 가능성**: 시작 화면, 이동 경로, 연결 페이지와 현재 위치 안내를 명시했다.
- **메뉴 깊이**: 3단계로 최대 5단계 이내다.
- **항목명 일관성**: 계층 구조·내비게이션·화면 구성에서 같은 명칭을 사용한다.
- **구조 변경 영향**: 상위 그룹 변경 시 로컬 메뉴·브레드크럼·관련 링크·화면 제목을 함께 점검한다.
- **웹·모바일 일관성**: 의미·우선순위·행동 순서를 유지하고 배치만 반응형으로 조정한다.
